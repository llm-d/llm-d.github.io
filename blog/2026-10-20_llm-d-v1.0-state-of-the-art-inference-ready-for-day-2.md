# llm-d v1.0: State-of-the-art inference, ready for Day 2

If the 0.x series was about building and hardening llm-d, v1.0 is about standing behind it. This release graduates the configuration API to v1, hardens the request path across clouds and accelerators, and brings four capabilities that production teams have been asking for: multi-tenant quality of service, zero-downtime operations, a stable foundation to build on, and agent-aware serving. Together they take llm-d from a stack that performs to a stack you can standardize on.

<!-- truncate -->

## Delivering state-of-the-art performance

Since the project launched in 2025, llm-d has grown from its first well-lit paths into a stack that delivers state-of-the-art inference across accelerators, model servers, and clouds: prefix-cache and load-aware routing, KV cache offloading, prefill/decode disaggregation, wide expert parallelism, and batch and async inference, across multiple model servers including vLLM and SGLang.

The proof came from the community running it in production, well beyond the founding contributors. DigitalOcean built its distributed inference stack on llm-d, citing native support for GPU-type heterogeneity, and used it to serve the trillion-parameter [Kimi K3 model](https://www.digitalocean.com/blog/serving-kimi-k3-inference-engine) across both AMD and NVIDIA hardware. A [KServe community case study](https://github.com/kserve/website/blob/main/blog/2026-04-21-production-grade-llm-inference-kserve-llm-d-vllm.md) coauthored by Tesla engineers reports a 3x increase in output tokens per second and a 2x reduction in time to first token on a Llama 3.1 70B deployment across AMD MI300X GPUs, after enabling prefix-cache-aware routing. [Prime Intellect](https://github.com/PrimeIntellect-ai/prime-rl) integrated llm-d into its large-scale reinforcement learning stack, pairing the llm-d router with prefill/decode disaggregation and KV offload. And IBM Research used llm-d to self-host a frontier open model, serving thousands of concurrent coding agents on an existing H100 fleet at several times lower cost per token than comparable commercial APIs, and to run open models for quantum error-correction research at roughly an order of magnitude lower inference cost than an all-proprietary setup.

The performance was there. v1.0 is about running it as a Day 2 operation.

## Why Day 2 is hard

Getting a model to serve fast is Day 1. Keeping it serving, for many tenants, through upgrades, under unpredictable load, is Day 2, and it is where most inference stacks show their seams.

A production fleet carries mixed traffic: latency-sensitive interactive requests next to bursty agent workloads that reuse enormous amounts of context and spawn parallel work without warning. Priorities compete, and under load something has to give. Upgrades and maintenance cannot mean downtime. Disaggregated deployments, which split prefill and decode across pools for efficiency, multiply the number of moving parts that have to roll forward together. And agentic traffic spends most of its compute on context rather than final tokens, so a stack that does not understand sessions and turns pays to recompute the same work again and again.

v1.0 addresses each of these directly.

## Multi-Tenant Quality of Service

A shared inference fleet has to keep latency-sensitive traffic responsive while absorbing bursty, unpredictable agent workloads. v1.0 makes that a first-class property of the router.

**Priority- and fairness-aware flow control** admits and orders requests so that interactive traffic is not starved by batch or agent bursts. **Program-aware fairness** keeps distinct workloads sharing a fleet without one crowding out the others, and **probabilistic admission with controlled load shedding** keeps the system responsive under overload rather than letting latency collapse. Flow-control configuration is now consolidated under a single `flowControl` surface, so operators tune one coherent policy instead of scattered knobs.

## Zero-Downtime Operations

Day 2 is where most serving stacks show their seams. v1.0 is built so upgrades and maintenance do not interrupt traffic.

**Router high availability with hot standby** keeps requests flowing if the active router is replaced or fails over. **Safe rolling updates** move a fleet to a new version without dropping in-flight work. For disaggregated serving, **DisaggregatedSet** manages prefill and decode replicas as one logical unit, with coordinated rollouts and lockstep upgrades, so a model that spans separate prefill and decode pools can be rolled forward as a single, consistent deployment. Disaggregation is no longer only a performance technique; it is now something you can operate.

## A Stable Foundation to Build On

**The configuration API graduates to v1.** Combined with a request path hardened for reliability, performance, and scalability, and validated across clouds and accelerators, v1.0 gives adopters a release they can standardize their platform on and build against with confidence. Topology-aware accelerator scheduling, including a DRA and DRANET well-lit path, rounds out a foundation that behaves consistently from a single node to a large heterogeneous fleet.

## Agent-Aware Serving

Agentic workloads reuse enormous amounts of context across turns, and most of the compute goes to handling that context rather than producing the final tokens. v1.0 serves this traffic natively.

**Session-aware routing** keeps a multi-turn conversation close to the server that already holds its cached context. **Turn-priority scheduling** lets the router reason about where a request sits in an ongoing exchange. And **native Responses API state**, including `previous_response_id`, lets agents carry context across turns so the stack can reuse it instead of recomputing it. For agent builders, that is less latency and lower cost without changing how they write their application.

## What This Means for You

**Platform teams** get a release they can standardize on: a v1 configuration API, high-availability routing, and rolling upgrades that do not interrupt traffic, validated across clouds and accelerators.

**ML infrastructure teams** get multi-tenant serving that stays predictable under load, and disaggregated deployments that are finally practical to operate, so a single fleet can carry mixed priorities without over-provisioning.

**Application and agent architects** get serving that understands sessions and turns, reuses context instead of recomputing it, and keeps interactive traffic responsive even while heavy agent workloads run alongside it.

## What Is Next?

v1.0 is a foundation, not a finish line. The community is already working toward active-active router configurations, inference request fail-over and migration, wider upstream vLLM wide-expert-parallelism coverage on managed Kubernetes, and expanded multimodal and audio serving. As new hardware and models arrive, the well-lit paths will grow to meet them, and the stack will keep evolving for peak performance across new architectures.
