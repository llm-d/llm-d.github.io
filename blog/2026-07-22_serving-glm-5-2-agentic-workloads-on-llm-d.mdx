# Serving GLM-5.2 for Agentic Workloads on llm-d

llm-d’s [well-lit paths](https://github.com/llm-d/llm-d/tree/main/guides) are tested, benchmarked recipes for serving large language models in production. The [agentic-serving path](https://github.com/llm-d/llm-d/blob/main/docs/well-lit-paths/workloads/agentic-serving.md) starts with the workload and combines the capabilities it needs into a deployment for each accelerator. This post applies that pattern to GLM-5.2-FP8 on H200, using the 219 production Claude Code sessions in SemiAnalysis’s Weka trace corpus.

At roughly 28 end-to-end output tokens per second per user, a 48-GPU llm-d deployment implies $0.07 per million input tokens and $2.53 per million output tokens at an H200 rental rate of $2.71 per GPU-hour. Z.ai's public GLM-5.2 row lists $1.40 input and $4.40 output; Claude Opus 4.8 lists $5 input and $25 output. These are sustained-load GPU-rental conversions, with prefill rental assigned to input and decode rental to output, not production TCO or API-equivalent pricing.

<!-- truncate -->

**TL;DR**

* **The workload is mostly reading.** Across 219 production Claude Code sessions, the median main-agent request carries 195K input tokens and returns 317 output tokens. Among main-agent turns, 96% reuse at least 90% of their input, and more than half of all requests belong to sub-agent groups.

* **Serving this workload** requires MLA to compress KV, wide expert parallelism to make room for it, prefix-aware routing to find it again, CPU offloading to keep more of it, separate prefill and decode pools to specialize differently, and optional MTP to reduce decode steps. All six are open in the llm-d stack.

* **More concurrent requests increase total output without materially slowing an active stream.** On the 64-GPU reference with three prefill instances and one decoder, output rises from 1,399 to 4,262 tok/s between concurrency 64 and 256 while median time between output tokens moves from 41 to 49 ms. Input makes up 98.6% of all tokens served. The queueing results show that prefill capacity is the limit.

* **Routing avoids redundant prefill.** Prefix-aware routing captures 96-97% of the reuse the workload makes available. In a separate paused-conversation run, turns with a cached prefix reach first token 2.8x faster than first turns without one.

* **CPU offloading keeps active prefixes reusable after HBM fills.** On the 24-GPU 1P1D DEP8/DEP16 layout at concurrency 32, it raises output 13%, cuts median time to first token 32%, and cuts median turn completion 27%, while median time between output tokens is unchanged. At concurrency 128, baseline output remains near 951 tok/s while offloading reaches 2,776 tok/s.

* **MTP moves the frontier; prefill width recovers interactivity.** With CPU offloading held constant on the 32-GPU 1P1D DEP16 topology, MTP delivers 1.7-2.0x aggregate output and 1.7-1.8x end-to-end output per user through concurrency 64. At concurrency 256, the 48-GPU 2P1D DEP16 configuration reaches 95% of the 64-GPU 3P1D DEP16 configuration's output and completes the median turn in 20.8 seconds versus 19.4 seconds.

* **At about 28 end-to-end output tok/s/user, the 48-GPU configuration implies approximately $0.07/M input and $2.53/M output at $2.71 per GPU-hour.**

* **Run it.** The [agentic-serving guides](https://github.com/llm-d/llm-d/tree/main/guides/agentic-serving) provide the serving pattern and composable MTP, CPU-offloading, and context-length components.

## The shape of agentic traffic

A coding agent's turn is mostly reading: a repository-scale context in, a tool call or a short diff out, then the whole context again next turn, slightly longer. The [Weka trace corpus](https://huggingface.co/datasets/semianalysisai/cc-traces-weka-with-subagents-051926) published by SemiAnalysis contains 219 production Claude Code sessions and 78,099 model requests. Each session captures interactive repository work: a main agent grows and reuses a working context across tool calls, pauses while tools run, and delegates work to Task-tool sub-agents that execute concurrently. The corpus preserves request timing, input and output lengths, per-request KV-block hashes, and the original sub-agent fan-out. It does not publish prompts or repository identities, so it characterizes the serving workload rather than the underlying coding-task categories.

Read the percentiles across each row, not down the column: the p90 input length and p90 pause do not belong to the same request or session. The wall-clock gap is the time between main-agent calls, not generation latency. Input-length growth is the increase from the previous main-agent turn, not a cache miss.

| Main-agent metric | p50 | p90 | p99 |
| :---- | :---- | :---- | :---- |
| Input tokens per request | 195K | 521K | 849K |
| Output tokens per response | 317 | 1,705 | 7,551 |
| Input-length growth from prior turn | 632 | 3,735 | 148K |
| Wall-clock gap between turns | 2 s | 24 s | 11.4 min |
| Turns per session | 107 | 354 | 992 |

*Token counts use different tokenizers. Input counts come from the o200k tokenizer, which the corpus uses to compute per-request KV block hashes; output counts are the values Anthropic's API reported. The raw table ratio of 195K to 317, about 615:1, therefore mixes units. A same-tokenizer input-to-output ratio is not reported here because Anthropic's production tokenizer is not public and this study did not calibrate one tokenizer against the other.*

**Most GPU work happens before the first output token.** The median main-agent request carries 195K input tokens and returns 317 output tokens, so serving is dominated by processing context. Output then arrives in short bursts between tool calls. Responsiveness depends on processing each context quickly and streaming its response steadily.

**Nearly everything has been read before.** A main-agent request is only 632 tokens longer than the preceding request at the median. When each request is matched to its best earlier turn, 96% reuse at least 90% of their input as a verbatim prefix; median reuse is 99.6%. A GPU cache hit avoids both recomputation and transfer. CPU or remote hits still have to move KV back to the GPU. Anthropic’s one-tenth price for cache-read input reflects the same reuse economics.

**Sessions pause, then burst.** Main-agent calls are two seconds apart at the median and eleven minutes apart at p99, while the median session lasts an hour. Cached state must survive those gaps to remain useful. Sub-agents add a second pressure: 40,367 of 78,099 requests arrive in groups, with seven requests per group at the median and 51 at p90. The serving layer receives that concurrency without advance notice.

One production session combines all three properties:

>
  A continuous 151.7-minute segment from one production session: 38 streaming main-agent requests and 5,527 sub-agent requests. The main-agent context grows to 754K tokens, while sub-agent work spans the full segment.

Prefix resets, where a turn shares less than half its input with any of its previous eight main-agent turns, occur on 2.8% of turns corpus-wide. Context compactions, where a context above 500K tokens returns below 30K, occur on 0.03% of turns. These are expected production pressures alongside sub-agent divergence and cache eviction under load. In the load benchmarks, measured reuse is governed by the admitted request distribution and cache churn, so routing on a single session-level prefix is insufficient.

The deployment has three jobs: keep repository-scale contexts in memory, reuse them on the next turn, and prevent long prefills from interrupting requests that are already streaming.

## Deployment architecture

The measured software stack is open source and runs on Kubernetes. The deployment uses CoreWeave CKS with InfiniBand:

| Layer | Component | Role |
| :---- | :---- | :---- |
| Model server | vLLM | FP8 inference, MLA KV cache, agentic parsers |
| Routing | llm-d EPP | prefix-cache-aware routing, P/D scheduling |
| KV transfer | NIXL | NIXL KV movement between prefill and decode; deployment network: InfiniBand |
| Tiered prefix cache | CPU DRAM cache + NVMe storage evictor | CPU-backed KV capacity below HBM; NVMe provisioned but inactive in these measurements |
| MoE compute | DeepEP + deep_gemm | expert parallelism across GPUs |
| Attention | FlashMLA Sparse | attention backend |
| Multi-node pods | LeaderWorkerSet | keeps the pods in each multi-node replica together so Kubernetes manages them as one unit |
| Benchmarking | AIPerf | load sweeps against the gateway |

The deployment combines four llm-d capabilities: wide expert parallelism, locality- and load-aware routing, a CPU-backed prefix cache, and separate prefill and decode pools. The topology chooses the number of prefill and decode instances. Configuration components enable CPU offloading, MTP, and longer context limits. Benchmarks run these disaggregated layouts on CoreWeave CKS with InfiniBand. Aggregate TP=8 appears only in the memory-profile check.

Each request moves through the same stack. MLA and wide expert parallelism determine how much context fits in HBM. Routing and CPU memory determine whether a saved prefix can be reused. Separate prefill and decode pools handle reading and generation. MTP reduces decode steps, while the number of prefill instances sets how much concurrent input work the deployment can absorb.

### Benchmark scope

Each benchmark admits only requests below its admission cap. The limited-input-length runs filter the trace at 142,000 tokens; the full-input-length runs admit longer contexts. The server sets max-model-len automatically in both, with GPU-memory utilization at 93.5% for prefill and 95% for decode. Each test answers a different question. The load sweep increases concurrency with completions near the corpus median, about 317 output tokens. ## Fitting repository-scale sessions in memory

Multi-head Latent Attention stores about 44 KB of KV state per token for GLM-5.2. In the measured 64-GPU 3P1D layout, measured capacity totals about 47.2M prefill-cache tokens and 17.3M decode-cache tokens beside the 753B model's weights. MLA stores 576 FP8 elements per layer per token: a 512-element latent plus 64 RoPE elements. Across 78 layers, that is 0.045 GB per 1K tokens. A counterfactual with 64 KV heads and 256-dimensional keys and values would use about 57x more KV memory; eight KV heads at those dimensions would use about 7x more.

For repository-scale sessions, MLA makes a multi-million-token working set practical. At concurrency 256, the 64-GPU 3P1D full-input-length run carries 25.5M logical tokens in flight, indicating the live request demand the cache must serve.

KV is allocated in 64-token blocks. Full-input-length runs set gpu-memory-utilization to 93.5% on prefill and 95% on decode. Depending on topology, each DEP16 prefill rank holds about 958K-990K KV tokens; each decoder rank holds about 1.078M. Across the 64-GPU 3P1D layout, that is about 47.2M prefill-cache tokens and 17.3M decode-cache tokens. These measured allocations include the three-token MTP head.

## Wide expert parallelism

Wide expert parallelism splits GLM-5.2's experts across GPUs at TP=1. Each GPU holds about 65 GiB of weights. In the full-input-length runs, KV uses about 40-41 GiB on each prefill GPU and 45 GiB on each decode GPU. The rest of HBM is used by the runtime and communication buffers.

The [guide’s default layouts](https://github.com/llm-d/llm-d/blob/main/guides/agentic-serving/glm-5.2-h200.md) use single-node DEP8 prefill instances and a two-node DEP16 decode pool, with LeaderWorkerSets and DP-aware scheduling. The measured 3P1D reference uses two-node DEP16 prefill instances. DeepEP sends tokens to the GPUs holding their experts over NVLink and InfiniBand, and deep_gemm runs the expert computation.

Width determines how much KV remains on each rank. In the limited-input-length sweep, the DEP8 prefill rank holds about 214K KV tokens and DEP16 about 990K. The narrower layout therefore reaches the CPU-backed cache sooner.

On the same hardware, aggregate TP=8 holds 598K KV tokens per node; DEP8 holds 1.77M, and a DEP16 node-share holds about 5.2M. The aggregate layout trades that 3× to 9× session-capacity gap for a single-node scheduling unit without the NVSHMEM heap or all-to-all fabric traffic.

## Routing turns back to their cache

Prefix-aware routing sends each turn to the prefill replica that already holds its growing context. **The prefill pool found 90.5-91.4% of reusable prefixes in GPU memory, capturing 96-97% of the reuse available in the workload.** Later turns with a cached prefix reached first token 2.8x faster than first turns without one. The llm-d Router schedules prefill and decode differently:

* Prefill placement looks at how much of a request's prefix is already in GPU or CPU memory, how many requests are queued, and how full the KV cache is. It sends the turn to the replica that offers the best balance of cache reuse and load.

* Decode placement balances GPU and CPU cache locality against the number of active requests.

The optimized-baseline configuration applies separate prefill and decode filters, and the router sees prefixes in both GPU and CPU memory. The load sweep keeps the corpus’s overlap pattern but uses shorter inputs, around 50K tokens at the median. Because each new suffix is a larger fraction of the request, at most 93.9–94.1% of the input can be reused.

GPU memory supplies 91.4% of reusable prefill prefixes at concurrency 64 and 90.5% at 256. That captures 96–97% of the reuse available in the test. Decode-local reuse falls as expected because NIXL moves KV from prefill to decode.

The paused-conversation run shows the latency effect: first turns without a cached prefix take 7.46 s median time to first token at about 20K input tokens; later turns with a cached prefix take 2.68 s on inputs up to four times longer. This is an observed workload result, not a matched cache-only control.

MTP puts more pressure on the same KV budget. On the 1P1D MTP configuration, GPU memory still supplies 92-93% of reusable prefixes through concurrency 64, while the workload's maximum possible reuse stays near 94%. The GPU share falls to 86.5% at concurrency 128 and 34% at 256 as HBM fills. A broader prompt-source counter reports 87% effective locality at concurrency 256, but it combines NIXL transfers with CPU restores and cannot identify the CPU-memory share. Through concurrency 64, routing captures 96-98% of the reuse available in the workload.

## Tiered prefix cache

CPU offloading extends prefix-cache capacity beyond HBM by restoring saved KV from CPU memory instead of recomputing evicted prefixes. **On the 24-GPU 1P1D DEP8/DEP16 layout at concurrency 32, CPU offloading raises output 13%, cuts median time to first token 32%, and cuts median turn completion 27%, while median time between output tokens is unchanged.**

<Figure
  src="/img/blogs/glm52-agentic-serving/offloading-attribution.png"
  alt="Matched 24-GPU baseline and CPU-offloading results"
>
  24-GPU 1P1D with DEP8 prefill and DEP16 decode; MTP is disabled in both runs. At concurrency 32, input distributions match within 1%. At concurrency 128, baseline output remains near 951 tok/s while CPU offloading reaches 2,776 tok/s; the fixed-duration stages complete different request slices, so the endpoint is a capacity comparison rather than a request-identical A/B. Higher output is better; lower latency is better.
</Figure>

Tool calls leave session KV idle, so the serving system may evict it from HBM before the next turn. CPU offloading keeps that KV in a per-rank DRAM pool and restores it when the conversation resumes. MultiConnector handles two paths: OffloadingConnector moves KV between GPU and CPU, while NIXL moves it between prefill and decode. The CPU tier evicts least-recently-used entries first. The increasing-load sweeps allocate 100 GiB per prefill rank; the paused-conversation run uses 150 GiB. Local NVMe sits behind CPU memory and receives no reads in these measurements.

The increasing-load sweep measures the capacity ceiling; the paused-conversation runs measure whether session state survives the gaps between turns.

### When HBM fills

Offloading does little until HBM fills. On the compact 16-GPU DEP8 topology, with MTP disabled in both runs, output is effectively unchanged at concurrency 16. At concurrency 128, offloading raises output 27% and cuts median turn completion 36%. Each stage runs for a fixed time, so the two runs may finish different requests. This compares how much work each configuration can handle, not the same requests one by one.

A separate dedicated DEP16 run shows the same pattern. At concurrency 256 on the 32-GPU 1P1D topology, offloading restores 2.8 TiB, raises output from 2,714 to 3,626 tok/s, and cuts median time to first token from 17.1 to 13.0 seconds. The dedicated 64-GPU 3P1D run shows the other regime: CPU memory accepts roughly 5 TB of writes over 24 minutes but serves no restores because the active prefixes still fit in HBM. CPU offloading adds capacity under HBM pressure; before that pressure, stores add modest overhead.

### Paused conversations

The paused-conversation test places two DEP8 prefill instances beside one DEP16 decoder, for 32 GPUs total. Each DEP8 rank has about one-third of DEP16’s KV capacity—220K versus 650K tokens—because it holds twice as much expert weight.

With 100–400 ongoing conversations and production-measured pauses of 2.1 s at the median and 25.8 s at p90, live session data reaches 1.4–5.6× GPU cache capacity. CPU memory holds the excess. As conversations resume, restore traffic rises from 3.5 to 22.4 GB/s.

At 400 conversations, every reused prefix is restored from CPU memory, totaling 9.7 TB in one stage, while the time between output tokens remains 34–37 ms. Restoring saved context is faster than recomputing it: 8.4 s versus 14.8 s median across the run, and 23.0 s versus 26.2 s at 400 conversations.

At 400 ongoing conversations on the mixed-width 2P1D topology and load, median time to first token reaches 124.5 s without CPU offloading versus 22.2 s with it. The p90 approaches six minutes, while the time between output tokens stays flat in both configurations. Pauses make recomputation expensive: each eviction forces the entire prefix to be rebuilt before the conversation can resume.

### Restore versus recompute

A controlled comparison on the mixed-width 2P1D topology isolates the cost of a cache miss. The GPU KV cache is limited to roughly 230K tokens per rank, slightly above its natural allocation, and CPU offloading is switched on or off for the same workload. At concurrency 32, nothing is evicted and the configurations match within 2%. At higher load, both GPU caches fall to single-digit hit rates; the only meaningful difference is whether a miss restores saved context or recomputes it.

Without offloading, a miss requires recomputing about 45K tokens. The server still produces a first token in about 5.7 s once work starts, but the client waits 59 s because 97 requests are queued for prefill. Throughput falls 78%, and the system completes 4.5x fewer turns. The time between output tokens remains 31-36 ms in both configurations because prefill and decode run on separate GPU pools.

Across the run, engine counters record 12.7 TB of KV, or 283M tokens, restored at 26 ms per GB. At concurrency 128, the CPU cache restores KV at 22.7 GB/s while the topology processes 474K prompt tokens per second.

The cache restores 222M tokens while serving 217M prompt tokens. That ratio exceeds 100% because the limited GPU cache can evict a block that was just restored, forcing it to be loaded again. Median time to first token remains 8.3 s, but the churn suggests that a retention policy better than LRU could reduce data movement.

### Adding prefill capacity

The narrowest layout puts the most pressure on CPU restore. At concurrency 256, 1P1D loads 7,774 GiB from CPU at about 9.0 GB/s on average and 19.87 GB/s at peak. The 2P1D layout cuts restore traffic 88%, raises output 41%, and cuts median time to first token 63%. The 3P1D layout cuts restore traffic by over 99% relative to 1P1D, but adds only 5% output over 2P1D. All three runs use a 100 GiB CPU tier per rank.

## Splitting prefill from decode

Prefill/decode disaggregation gives input processing and token generation separate GPU pools, so each phase has independent capacity and scheduling.

**Across the disaggregated sweep, output throughput tripled while median time between output tokens stayed between 41 and 49 ms, consistent with phase isolation.**

There is no matched aggregate control, so this sweep measures scaling within the P/D layout rather than a controlled P/D-versus-aggregate gain. Prefill uses deep_gemm with deepep_high_throughput; decode uses deepep_low_latency; NIXL moves KV between the pools. Both pools use wide expert parallelism over InfiniBand.

The output rate hides most of the work. At concurrency 256, each GPU serves 4,788 total tokens per second, and 98.6% are input. For this workload, the cluster is primarily buying prefill capacity.

A decode speedup shifts pressure toward prefill, as the speculation results show.

## Speculation and tool calling

Multi-token prediction drafts and verifies several tokens in one decode step, reducing sequential decode steps when the drafts are accepted.

**With CPU offloading held constant on the 32-GPU 1P1D topology, MTP delivers 1.7-2.0x aggregate output and 1.7-1.8x end-to-end output per user through concurrency 64; at concurrency 64, median turn completion falls 34% and p90 falls 44%.**

The 32-GPU 1P1D comparison keeps CPU offloading enabled in both runs, so the measured difference comes from MTP. A separate run disables both features and serves as the overall baseline. The measured configuration drafts three extra tokens per decode step and keeps KV in FP8. The 2P1D topology shows similar MTP gains through concurrency 64.

Tool-call validity remains unquantified. Multi-token deltas can break streaming parsers that expect one token at a time (related reports for other model/parser combinations: [vLLM #42400](https://github.com/vllm-project/vllm/issues/42400) on GLM-5.1, [#41967](https://github.com/vllm-project/vllm/issues/41967) on Gemma4). ## Sizing prefill and decode capacity

**Prefill and decode replicas remove different queues. The full-input-length sweep compares prefill and decode allocation under DEP16; the limited-input-length sweep widens decode and then prefill. Results are comparable only within the same test.**

### Adding prefill or decode capacity

**Prefill replicas shorten the wait before generation; decode replicas raise output capacity.** The full-input-length sweep keeps every instance at DEP16 and compares 1P1D, 2P2D, 3P1D, and 3P2D with native MTP and CPU KV offloading enabled.

At concurrency 128, keeping three prefill replicas fixed and adding a second decoder raises output from 6,281 to 7,598 tok/s (+21%) and end-to-end output per user from 36.6 to 44.2 tok/s/user (+21%). Median turn completion falls from 14.0 to 11.5 seconds, while median time between output tokens falls from 19.1 to 15.5 ms. Median time to first token remains near 2.1 seconds.

Prefill width changes a different part of the turn. With two decoders fixed, moving from 2P2D to 3P2D cuts median time to first token from 2.70 to 2.12 seconds and CPU-to-GPU restore traffic from 759 to 45 GiB; median time between output tokens stays near 15.4 ms. In this sweep, at the same 64-GPU budget, 2P2D produces 8% more output and completes the median turn 10% sooner, while 3P1D lowers median time to first token 19% and restore traffic 63%.

### Where the bottleneck moves

**Decode and prefill width remove different queues.** The limited-input-length sweep keeps native MTP and CPU KV offloading enabled while widening one side of the deployment at a time.

At concurrency 128, widening the DEP8 decoder to DEP16 raises output from 1,501 to 3,233 tok/s and cuts the decode queue from 39 to 3 requests. The narrow prefill pool still has 137 requests waiting and restores 7,229 GiB of KV from CPU memory.

Widening prefill from DEP8 to DEP16 moves the active KV set back into HBM. Per-rank prefill capacity rises from about 214K to 990K KV tokens, CPU restore traffic falls from 7,229 to 50 GiB, and median time to first token falls from 20.9 to 2.38 seconds. Output reaches 5,647 tok/s.

A second DEP16 prefill instance removes the remaining restore traffic. At concurrency 128, 2P1D reaches 6,647 output tok/s and 1.59 seconds median time to first token. The 32-GPU 1P1D topology delivers 85% of that output with one-third fewer GPUs; the 48-GPU 2P1D topology buys lower latency and more prefill headroom. Against the 48-GPU baseline with both features disabled, the optimized 32-GPU layout produces 54% more output, delivers 51% more end-to-end output per user, and completes the median turn 18% sooner while using one-third fewer GPUs; median time to first token is 2.38 versus 1.26 seconds. The fixed-duration stages do not complete the same request slice, so these are operating-point comparisons rather than request-identical A/Bs.

## What it costs at an interactivity target

At the operating point used here, the 48-GPU 2P1D topology with MTP and CPU offloading serves 359K input and 4,770 output tokens per second at concurrency 128, while delivering 28.0 end-to-end output tokens per second per user. End-to-end throughput includes queueing and prefill, so it is the user-visible rate. The cost split follows the disaggregated pools: 32 prefill GPUs are charged against input tokens and 16 decode GPUs against output tokens.

At a 28-30 tok/s/user interactivity target, 3P1D implies $0.10 per million input tokens and $2.45 per million output tokens; 2P1D implies approximately $0.07 per million input tokens and $2.53 per million output tokens at an H200 rental rate of $2.71 per GPU-hour. The 48-GPU 2P1D configuration is the balanced point: extra prefill capacity changes output cost little, while less prefill capacity reduces aggregate output at the target.

Input tokens are logical tokens: cached prompt tokens count at their full prompt length, not by the bytes restored from cache.

[Z.ai](https://docs.z.ai/guides/overview/pricing) lists its GLM-5.2 API at $1.40 per million input tokens, $0.26 cached input, and $4.40 per million output tokens. [Anthropic](https://platform.claude.com/docs/en/about-claude/pricing) lists Claude Opus 4.8 at $5 input and $25 output, with cache reads at $0.50 per million tokens. At the stated rental rate, self-hosted output is about 57% of Z.ai's public GLM-5.2 rate and about one-tenth of Opus. Input is about one-twentieth of Z.ai's list rate and about one-quarter of its cached-input rate. Input accounts for 98.7% of served tokens at this operating point; under the 32-prefill/16-decode allocation, prefill accounts for two-thirds of GPU rental.

### Cost basis and limits

These figures assume that the cluster sustains the measured load 24/7. Lower utilization raises effective cost in inverse proportion. The prices cover GPU rental only; storage, egress, engineering, support, and taxes are excluded. The input/output split assigns each P/D pool's cost to the tokens it processes; another allocation changes the two columns, not total cluster cost. API rates include managed operations, autoscaling, service commitments, and provider margin. Spot rates also carry interruption and availability risk. The comparison describes token economics at a fixed operating point, not full total cost of ownership or an API-equivalent service.

## Conclusion

Agentic serving depends on input reuse as much as decode speed. On the 64-GPU reference, increasing concurrency from 64 to 256 triples output while median time between output tokens stays between 41 and 49 ms. Because there is no matched aggregate control, this demonstrates scaling within P/D rather than a measured P/D-versus-aggregate gain. At concurrency 256, the 48-GPU 2P1D topology reaches 95% of the 64-GPU 3P1D topology's output and completes the median turn within 1.4 s of it.

Each optimization removes a different bottleneck. MLA and wide expert parallelism make room for long contexts, while routing and CPU memory keep them reusable. Separate prefill and decode pools stop long reads from disrupting generation; MTP reduces decode steps; and additional prefill replicas absorb higher concurrency.

At high concurrency, queueing on the fixed DEP16 decoder limits how much generation speed reaches each user. Wider decode layouts are the remaining capacity axis; the baseline family’s asymmetric EP8/EP16 layouts provide the comparison points.

The agentic-serving cookbooks include [Nemotron-3-Ultra-550B on H200](https://github.com/llm-d/llm-d/blob/main/guides/agentic-serving/nemotron-3-ultra-550b-h200.md), with P/D disaggregation and CPU KV offloading, and [Qwen3-Coder-480B on TPU v7](https://github.com/llm-d/llm-d/blob/main/guides/agentic-serving/qwen3-coder-480b-tpu.md), with routing and CPU offloading. The GLM-5.2 H200 configuration follows the same agentic-serving pattern.
