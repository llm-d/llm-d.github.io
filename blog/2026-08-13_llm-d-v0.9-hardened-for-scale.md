# llm-d v0.9: Hardened for Scale

If v0.8 was about declaring llm-d an inference control plane, v0.9 is about proving it at production scale. The router gains coordinator high availability so that no single endpoint picker failure drops traffic. Flow control ships with bounded defaults that protect clusters out of the box. A formal plugin lifecycle gates experimental extensions behind explicit opt-in. And KEDA replaces Prometheus Adapter as the autoscaling foundation, aligning llm-d with the Kubernetes-native scaling ecosystem.

The v0.8 release previewed four themes for v0.9 — agentic inference, RL workflow maturity, scaling and hardening, and accelerator expansion — and this release delivers on all four. Disaggregated inference now works without RDMA fabric. The router scores endpoints by actual GPU utilization, not just queue depth. Diffusion model routing extends the control plane to image generation. And new well-lit paths land for GB200, GB300, Intel XPU, ROCm, and TPU v7 hardware. The reinforcement learning story advances from feasibility proof to architectural foundation, with a time-slicing proposal and Python inference scheduler integration underway.

## Production-Hardened Control Plane

The most consequential changes in v0.9 are about what happens when things go wrong.

**Coordinator high availability** introduces a multi-EPP topology where non-leader replicas keep their datastores populated and route traffic rather than returning 503. If the leader fails, standby replicas continue serving without interruption. The new `--drain-timeout` flag enables graceful shutdown — the endpoint picker stops accepting new requests while draining in-flight traffic, preventing the connection resets that operators reported during rolling updates.

**Plugin stability lifecycle** formalizes the maturity of every router plugin as Alpha, Beta, or Stable. Alpha plugins require `--allow-experimental-plugins` to activate, preventing accidental use of unproven extensions in production. Automated dependency validation ensures that a plugin's prerequisites are satisfied before the router starts, replacing runtime crashes with clear startup errors.

**Flow control** ships with production-safe defaults for the first time. `defaultRequestTTL` defaults to 60 seconds and per-band `maxRequests` to 5000, bounding queue growth without operator intervention. Rejection codes now distinguish an empty endpoint pool (503) from retryable backpressure (429), giving load balancers and clients the signal they need to back off correctly. Priority-aware stepped gating and soft-reflective-ceiling policies give operators finer control over how traffic sheds under saturation.

## Disaggregation: Beyond RDMA

Disaggregated prefill/decode has been one of llm-d's deepest investments. v0.9 removes the biggest barrier to adoption: the RDMA fabric requirement.

**RDMA-free KV transfer** through the new offloading connector on the disaggregation sidecar enables KV cache transfer over standard TCP networking with data-parallel support. Clusters without InfiniBand or RoCE — which includes most cloud environments outside of HPC-optimized node pools — can now run disaggregated inference with the same routing intelligence. This is a meaningful expansion of where P/D disaggregation is deployable.

**DisaggregatedSet revision routing** enables consistent rolling updates across prefill and decode pods. During a model version rollout, the router understands which pods belong to which revision and routes accordingly, preventing the request failures that occurred when a prefill pod sent KV cache to a decode pod running a different model checkpoint. **Topology-aware routing** extends this with a new filter and scorer that understands the physical P/D topology for placement decisions. **CPU-tier-aware pull-source selection** distributes KV transfer load proportionally across available sources, avoiding the hot spots that emerged when all decode pods pulled from the same prefill replica.

## Routing Intelligence

The router's scheduling pipeline gains several capabilities that move it from heuristic-based to measurement-based decisions.

**GPU utilization-aware routing** uses the DCGM extractor and a generic endpoint-attribute filter and scorer to route requests based on actual GPU utilization metrics rather than proxy signals like queue depth. Operators can now express routing policies in terms of the resource they actually care about — GPU compute — rather than inferring it from request counts.

**Session affinity** via the `session_id` strategy keeps multi-turn conversations on the same backend where prior KV cache is resident. The **header-based profile handler** selects a scheduling profile per request from a header, enabling a single router deployment to apply different routing strategies to different traffic classes without separate endpoint picker instances.

**The utilization filter** replaces the former active-request-filter with a unified mechanism that caps endpoints on any combination of active, running, waiting, and KV-cache utilization. This consolidates what was previously multiple independent filters into a single, composable policy.

## Multimodal and Diffusion Model Support

v0.9 extends the control plane to workload types that previous releases did not address.

**Image generation routing** adds OpenAI-compatible `/v1/images/generations` endpoint handling for diffusion backends such as vLLM-Omni. The router now understands the different resource profile of image generation — longer compute, no KV cache, different batching semantics — and schedules accordingly. **Video input** support in approximate prefix match enables the router to compute cache affinity for video-bearing multimodal requests, extending the prefix-cache optimization to vision-language models processing video.

**E/P/D heterogeneous serving** with SGLang enables encode, prefill, and decode stages to run on mixed GPU and XPU hardware, with the router managing request flow across the heterogeneous topology. **Multimodal predicted latency** extends the latency predictor to account for the additional compute cost of processing image and video tokens alongside text, improving routing accuracy for multimodal workloads.

## KEDA-Native Autoscaling

v0.9 begins the migration from Prometheus Adapter to KEDA as the autoscaling foundation.

New guides land for **KEDA + EPP pool-level saturation metrics**, where the endpoint picker exposes queue depth, in-flight request counts, and KV-cache pressure as KEDA-compatible scaling signals. The router becomes the source of truth for scaling decisions rather than relying on Prometheus queries against model server metrics. **SLO-driven autoscaling** combines KEDA with the predicted latency scorer, scaling based on whether the deployment can meet its latency targets rather than reacting to utilization thresholds after they are breached.

Queue-based KEDA + EPP autoscaling now runs in nightly CI on OpenShift with GPU, validating that the scaling path works end-to-end on every commit. The Workload Variant Autoscaler continues to support the existing Prometheus Adapter path for operators who have not yet migrated.

## Observability and Security

Production operations require visibility. v0.9 closes the observability gaps that operators reported during v0.8 deployments.

**End-to-end tracing** adds OpenTelemetry spans over the scoring path and propagates trace context through the full P/D transfer chain — from request arrival through prefill scheduling, KV transfer, and decode completion. For the first time, operators can trace a single request across the entire disaggregated inference pipeline in their existing tracing infrastructure.

**mTLS** for the EPP metrics endpoint and scrape sources hardens the security posture of the control plane. Configurable ext_proc TLS minimum version and cipher suites give security teams the controls they need. **Bounded metric cardinality** prevents label explosion on model-name and fairness-id dimensions, addressing the Prometheus memory issues that operators with many models or tenants encountered. The **Grafana dashboard** moves from the router repository to the main llm-d repo, and per-guide troubleshooting documentation ships for workload autoscaling and P/D disaggregation.

## Reinforcement Learning: From Feasibility to Architecture

v0.8 proved that llm-d could serve inference outside Kubernetes with the FileDiscovery plugin. v0.9 advances the RL story from feasibility demonstration to architectural foundation.

The **Python inference scheduler** integration brings llm-d's routing logic into Python-native RL training loops, where the overhead of a Go binary and gRPC boundary is unacceptable for tight rollout-generation cycles. The **time-slicing architecture proposal** lays out how a single GPU fleet can alternate between training and inference phases within an RL step — serving rollout requests during the generation phase and returning GPUs to the training framework for gradient updates. This is the pattern that frameworks like veRL and OpenRLHF need to run efficiently on shared infrastructure.

Work is underway on **veRL end-to-end integration** with GRPO training and NCCL weight synchronization. The goal is a reference deployment where veRL drives the training loop, llm-d manages the inference fleet with prefix-cache-aware routing, and weight updates flow from trainer to servers without restarting the inference engine. The full RL story — time-slicing, multi-framework support, hardened weight sync — targets v0.10.

## New Well-Lit Paths and Accelerator Coverage

Each release expands the set of tested, documented deployment patterns. v0.9 adds coverage across new hardware generations and deployment topologies.

**NVIDIA GB200 (A4X) and GB300 (A4X-Max)** receive P/D disaggregation overlays with DRA and RDMA recipes, bringing disaggregated inference to NVIDIA's latest data center hardware. **Intel XPU** expands to wide expert parallelism, tiered prefix cache with the lmcache connector, and multimodal optimized baseline — making XPU a viable platform for all three well-lit paths. **ROCm** gains predicted latency routing and P/D disaggregation with the MoRI connector. **TPU v7** adds disaggregated P/D benchmarks for the agentic serving path.

**LiteLLM and Kong AI Gateway** integration guides land for operators who want to front llm-d with an API management layer that handles authentication, rate limiting, and model routing across multiple providers. **SGLang** adds managed Lustre L3 offloading support and native filesystem offloading, expanding the tiered caching story to SGLang backends. The default vLLM image updates to v0.26.0.

## What This Means for You

**Platform teams** running llm-d in production gain coordinator HA, flow control defaults that protect clusters without manual tuning, and a plugin lifecycle that prevents experimental code from reaching production unless explicitly enabled. The KEDA migration provides a standard autoscaling interface that integrates with existing Kubernetes scaling infrastructure. The metric renames in this release (EPP KV metrics move to the `llm_d_router_epp` subsystem) require dashboard and alert updates — deprecated aliases are available during the transition.

**ML researchers** can now run disaggregated inference without RDMA fabric, removing the hardware barrier that limited P/D disaggregation to HPC-class clusters. The RL architectural work — Python scheduler, time-slicing proposal, veRL integration — signals where llm-d is heading as inference infrastructure for training loops. New accelerator overlays for GB200, GB300, and expanded XPU coverage mean more hardware options with tested deployment recipes.

**Application architects** building multimodal and generative applications get routing support for diffusion models alongside language models on shared infrastructure. Session affinity and header-based profile selection enable sophisticated traffic management for agentic and multi-turn workloads. End-to-end OTel tracing through the disaggregated pipeline provides the observability needed to debug latency issues in production.

## What Is Next?

The [v0.10 milestone](https://github.com/llm-d/llm-d/milestones) targets September and deepens three areas this release established.

**RL time-slicing and weight synchronization** are the headline. v0.9 laid the architectural foundation; v0.10 targets a working end-to-end time-slicing deployment where GPUs alternate between RL training and inference rollout generation within a single step. Hardened NCCL weight sync — packed tensors, multi-node — and validation with a second RL framework beyond veRL are the concrete deliverables.

**Model server configuration API** moves toward a 1.0 specification. The goal is a standardized introspection and configuration interface that the control plane uses to query model server capabilities, set runtime parameters, and manage engine lifecycle — independent of whether the engine underneath is vLLM, SGLang, or TensorRT-LLM. This is a prerequisite for the engine lifecycle management that time-slicing requires.

**KV-cache observability** graduates from per-guide metrics to a unified observability framework. Storage checkpoint indexing, dynamic speculative TTL, and a dedicated observability epic in the KV cache layer will give operators visibility into cache hit rates, tier utilization, and eviction patterns across the full multi-tier hierarchy.
