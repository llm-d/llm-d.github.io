# Bringing First-Class SGLang Serving to llm-d: Engine-Agnostic Routing, Disaggregated Wide-EP, and Tiered KV Cache Offloading

In [Serving GLM-5.2 for Agentic Workloads on llm-d](/blog/serving-glm-5-2-agentic-workloads-on-llm-d), we showed how `llm-d` serves long-context coding agents on NVIDIA H200 GPUs with vLLM—combining disaggregated prefill and decode pools, wide expert parallelism, prefix- and load-aware routing, and tiered KV caching. Since then, contributors from the `llm-d` and [SGLang](https://github.com/sgl-project/sglang) communities have made **SGLang** a first-class, Kubernetes-native inference engine in `llm-d`'s [GLM-5.2 well-lit path](https://github.com/llm-d/llm-d/tree/main/guides/models/glm-5-2), the project's tested reference deployment. We also measured SGLang's multi-tier KV cache on single-replica and multi-replica clusters. This post tells that story in three parts:

1. **Engine-agnostic `llm-d` architecture:** how `llm-d` decouples Kubernetes workload orchestration, prefix-affinity routing, and disaggregated serving from individual model servers so vLLM and SGLang share a common operational model.
2. **First-class SGLang integration:** how the SGLang and `llm-d` communities adapted SGLang's Wide-EP runtime to work natively with `llm-d`'s Kubernetes routing and disaggregated serving.
3. **Tiered KV-cache offloading (`L1` → `L2` → `Shared L3`):** how pairing SGLang's hierarchical KV cache (`HiCache`) with `llm-d`'s prefix-aware routing and Kubernetes failover keeps long agent sessions cached across host RAM and shared storage—surviving high concurrency, pod evictions, and cold restarts.

## 1. `llm-d` Architecture and Engine-Agnostic Design

A central design goal of `llm-d` is to give platform teams a unified Kubernetes control and routing layer regardless of which inference engine runs inside the serving containers. Rather than maintaining separate gateways, autoscalers, or cache-routing stacks per engine, `llm-d` separates cluster-level serving primitives from engine-specific execution (Figure 1):

* **Declarative disaggregated orchestration (`DisaggregatedSet` + `LeaderWorkerSet`):** Multi-node prefill and decode pools run as native Kubernetes workloads with coordinated gang scheduling, revision-aware rolling updates, and Dynamic Resource Allocation (`DRA`) for GPUs and RDMA NICs. Scaling from a single-replica `16`-GPU deployment (`p1w1d1w1` = 1 prefill replica of 1 node + 1 decode replica of 1 node) to multi-replica or multi-node Wide-EP layouts (`p2w1d1w2` on `32` GPUs, `p2w2d2w2` on `64` GPUs) uses the same declarative overlays and operational lifecycle across engines.
* **Per-DP-rank `InferencePool` endpoint discovery:** Rather than exposing a multi-GPU pod as a single aggregated endpoint, `llm-d` registers each attention-DP rank as its own `InferencePool` endpoint (`DP-per-endpoint`, as detailed in the [earlier GLM-5.2 post](/blog/serving-glm-5-2-agentic-workloads-on-llm-d#fitting-repository-scale-sessions-in-memory)). This lets the router see and target each GPU's separate KV cache directly.
* **Pluggable `Endpoint Picker` (`EPP`) routing pipeline:** Fronted by Envoy and the Kubernetes Gateway API, the `EPP` inference router parses each request and tracks, per rank, which prefixes are cached and how many tokens are in flight. It sends prefill requests back to the rank that holds the warm prefix, spreads decode requests by active request count, and coordinates the prefill-to-decode transfer.

Because `llm-d` defines these primitives—per-DP-rank endpoints, separate prefill and decode scheduling profiles, and composable Kustomize components—at the platform layer, adding SGLang did not require a parallel routing stack or custom operator workflow. Once SGLang exposed the same per-rank endpoint and disaggregation contracts, users could choose SGLang as their serving backend under `llm-d`'s Kubernetes control plane—getting out-of-the-box Wide-EP dispatch on RoCE networks and tiered KV-cache offloading with SGLang's Hierarchical Cache (`HiCache`).

## 2. First-Class SGLang Integration in `llm-d`

SGLang could already run GLM-5.2 Wide-EP as a standalone server, but integrating it into `llm-d` exposed a core boundary mismatch. In a Wide-EP (`DEP`) deployment, MoE experts are shared across GPUs, while each attention-DP rank owns a separate KV cache. Because `llm-d` routes requests, tracks prefix locality, and pairs prefill with decode (`P/D`) at the per-DP-rank level, a single node-level endpoint is not enough. Every DP rank needs to act like an independent server—with its own port, its own `P/D` pairing handshake, and its own health and observability signals.

The goal of our engineering work was making SGLang's Wide-EP runtime fit cleanly into `llm-d`'s Kubernetes control plane:

| **Pain we hit** | **What we changed** | **What operators get** |
| :--- | :--- | :--- |
| **One node-level port hid eight separate KV caches behind a single endpoint.** | Leveraged the embedded Rust HTTP server for each DP rank with per-rank warmup readiness. | Every DP rank across single- and multi-node pools is a routable `InferencePool` endpoint. |
| **`P/D` pairing only worked on rank 0; routing to any other rank failed during the handshake.** | Replicated `P/D` pairing state across all rank listeners, carried routing metadata across OpenAI and native APIs, used standard Linux `DMA-BUF` RDMA for KV transfers, and added clean decode cancellation on prefill failure. | `EPP` can pair any prefill rank with any decode rank across nodes on standard GPU nodes. |
| **Operators and routers lacked per-rank visibility into serving and cache hits.** | Surfaced `cached_tokens` in responses, correlated `P/D` traces and logs across nodes, and added DP-aware KV-event handling in `EPP`. | Per-endpoint visibility in logs and traces, supporting zero-scrape approximate routing today and preparing exact KV-event tracking. |

## 3. Tiered KV-Cache Offloading and Multi-Replica Performance

With SGLang running natively behind `llm-d`'s prefix-aware router, the remaining bottleneck for agentic serving is **KV-cache capacity and survival**. Using SGLang's **HiCache** on the prefill pool, we evaluate a three-tier KV-cache memory hierarchy on 8-GPU NVIDIA H200 nodes (`DEP8` prefill, tested on GKE A3 Ultra with ConnectX-7 RoCE and a `9,000 GiB` Google Cloud Managed Lustre volume):

* **`L1` — GPU HBM (Baseline):** Fast GPU-resident KV + DSA indexer pool (`261K` tokens per GPU, `2.09M` tokens per 8-GPU prefill pod — enough for roughly `20–30` repository-scale sessions).
* **`L2` — Host RAM (`hicache`):** Per-rank pinned host memory (`100 GB/rank` default = `17.5M` `L1+L2` tokens/pod) transferred over direct PCIe Gen5 DMA.
* **`L3` — Shared Storage (`hicache-fs`):** SGLang's file backend on a `ReadWriteMany` PersistentVolumeClaim (`~163M` tokens across the `9,000 GiB` volume), backed by a client-side metadata cache so each rank remembers pages it has already seen. Because GLM-5.2's MLA KV representation is identical across attention-DP ranks, page files carry no rank suffix — creating **one deduplicated cache pool shared across every rank and prefill replica**.

### Extending single-node memory with Host RAM (16x H200 `p1w1d1w1`)

We measured how `L2` host RAM and `Shared L3` remote storage behave on the default 16-GPU single-replica layout (`p1w1d1w1`: 1x `DEP8` prefill pod + 1x `DEP8` decode pod) under the `900s` [AIPerf `inferencex-agentx-mvp` benchmark](https://github.com/ai-dynamo/aiperf/blob/main/docs/tutorials/agentx-mvp.md) on the [`cc-traces-weka-062126`](https://huggingface.co/datasets/semianalysisai/cc-traces-weka-062126) Claude Code trace corpus with a `142K` context cap, swept from concurrency `16` to `128`:

<Figure

  alt="L2 host RAM eliminates the L1 thrashing cliff on a single 16-GPU replica"
  size="wide"
>

</Figure>

| **Single-Replica `p1w1d1w1`** | **`c16` → `c128` TTFT P50 / P90 (`s`)** | **`c16` → `c128` Output (`tok/s`)** | **`c16` → `c128` Server Cache Hit** |
| :--- | :--- | :--- | :--- |
| **`L1` GPU HBM only** | `3.07 / 10.46` → **`174.19 / 266.75`** | `182.1` → `747.3` (`c32` peak) → **`319.0`** *(thrashing)* | `92.3%` → **`6.0%`** |
| **`L1 + L2` Host RAM** | `3.05 / 5.85` → **`20.09 / 48.61`** | `188.8` → **`1,256.8` (`3.94x L1` at `c128`)** | `94.8%` → **`88.5%`** |
| **`L1 + L2 + Shared L3`** | `3.49 / 8.21` → `26.03 / 58.58` | `183.8` → `1,139.7` | `94.9%` → **`90.3%`** |

Past concurrency `32`, active sessions exceed the `2.09M`-token `HBM` budget and evict one another (`6.0%` hit and `174.2 s` median TTFT at `c128`). Offloading to `L2` host RAM preserves `85%–95%` cache reuse across the full sweep, cuts `c128` median TTFT **`8.7x`**, and raises output **`3.94x`** — whereas enabling write-through `L3` on a single warm pod adds `~26%–30%` to median TTFT and trims `c128` output by `~9%` for no significant extra benefit.

### Multi-replica Shared L3 (32x H200 `p2w1d1w2`)

`Shared L3` pays off across multi-replica failover, pod evictions, and cold restarts. To test this, we deploy `p2w1d1w2` (two `DEP8` prefill pods and one 2-node `DEP16` decode pool). We measure both sustained load (`64` and `128` concurrent sessions) and a live failover test: with `24` active `~98K`-token sessions split across `prefill-0` (`11` sessions) and `prefill-1` (`13` sessions), we delete `prefill-0` at `t = 95 s` so `EPP` moves all `11` of its sessions onto `prefill-1`:

| **Scenario (`32`x H200 `p2w1d1w2` unless noted)** | **`L1 + L2` (Local Pod RAM)** | **`L1 + L2 + Shared L3` (`hicache-fs`)** | **Key Takeaway** |
| :--- | :--- | :--- | :--- |
| **Sustained `c64`** (`900s`) | **TTFT (P50 / P90):** `3.10 / 8.36 s`<br />**Output: `1,105 tok/s`** (`91.0%` hit) | **TTFT (P50 / P90):** `3.91 / 10.55 s`<br />**Output:** `1,055 tok/s` (`92.5%` hit) | `<5%` throughput cost for cross-pod cache sharing |
| **Sustained `c128`** (`900s`) | **TTFT (P50 / P90): `3.43 / 16.05 s`**<br />**Output: `1,903 tok/s`** (`90.7%` hit) | **TTFT (P50 / P90):** `5.69 / 24.63 s`<br />**Output:** `1,691 tok/s` (`93.4%` hit) | **`5.9x` lower TTFT** & **`+51%` output** vs. `16`-GPU `p1w1d1w1` |
| **Live pod eviction** (`11` sessions → `prefill-1`) | **TTFT (P50):** `38.35 s` (`37.5 s` at `t=150s`)<br />**Cache Hit: `0%`** (full recompute) | **TTFT (P50): `28.76 s`** (**`3.82 s`** at `t=150s`)<br />**Cache Hit: `99.94%`** (from `L3`) | Offloads recovery to `L3` I/O; **`-25%` P50 TTFT** and cuts recovery time roughly in half |
| **Cold replica / restart** (`16` sessions, `~92K` input tokens) | **TTFT (P50):** `38.84 s`<br />**Cache Hit: `0%`** (full recompute) | **TTFT (P50): `16.82 s` (`-57%`)**<br />**Restored: `97.8%`** of prefixes | **`2.31x` faster** cold-pod recovery |

Scaling out to `p2w1d1w2` cuts `c128` median TTFT **`5.9x`** (`3.43 s`, `1,903 tok/s`). While `Shared L3` adds steady-state overhead without failures (`+26%` to `+66%` median TTFT, `<5%` to `11%` lower output), it restores **`99.94%`** of failed-over prefix tokens during pod loss and cuts cold-start TTFT by **`57%`**—so operators should run **`L1 + L2`** on steady single-replica pods and add **`Shared L3`** when resilience to Spot preemptions, upgrades, or multi-replica failover matters (full overlays are in [`guides/models/glm-5-2`](https://github.com/llm-d/llm-d/tree/main/guides/models/glm-5-2)).

## Running the Recipe

Deploying the SGLang GLM-5.2 stack on `llm-d` takes two steps—installing the standalone inference router with [`sglang.values.yaml`](https://github.com/llm-d/llm-d/blob/main/guides/models/glm-5-2/router/sglang.values.yaml), and applying a deployment overlay from [`guides/models/glm-5-2`](https://github.com/llm-d/llm-d/tree/main/guides/models/glm-5-2) (choose one of the two options below):

```bash
export REPO_ROOT=$(realpath $(git rev-parse --show-toplevel))
export GUIDE_NAME=glm-5-2
export NAMESPACE=llm-d-glm-5-2
source ${REPO_ROOT}/guides/env.sh

# 1. Deploy the engine-agnostic llm-d router with the SGLang Wide-EP configuration:
helm install ${GUIDE_NAME} \
  ${ROUTER_STANDALONE_CHART} \
  -f ${REPO_ROOT}/guides/recipes/router/base.values.yaml \
  -f ${REPO_ROOT}/guides/models/${GUIDE_NAME}/router/${GUIDE_NAME}.values.yaml \
  -f ${REPO_ROOT}/guides/models/${GUIDE_NAME}/router/sglang.values.yaml \
  -n ${NAMESPACE} --version ${ROUTER_CHART_VERSION}

# 2. Option A: 32-GPU multi-replica p2w1d1w2 with L1 + L2 host RAM (use deployments/p1w1d1w1 for the 16-GPU layout):
kubectl apply -n ${NAMESPACE} \
  -k ${REPO_ROOT}/guides/models/glm-5-2/modelserver/gpu/sglang/deployments/p2w1d1w2

# 2. Option B: 16-GPU p1w1d1w1 with Shared L3 (adds components/hicache-fs).
#    Needs a ReadWriteMany PVC named llm-d-kv-cache-storage. For multi-replica
#    Shared L3, add the same component to the p2w1d1w2 overlay.
kubectl apply -n ${NAMESPACE} \
  -k ${REPO_ROOT}/guides/models/glm-5-2/modelserver/gpu/sglang/deployments/benchmark/hicache-fs/p1w1d1w1
```

## Conclusion

Bringing first-class SGLang serving to `llm-d` started with a simple constraint: supporting a second engine could not mean building a second platform. Contributors added per-rank Rust endpoints and replicated `P/D` pairing state in SGLang. As a result, `llm-d` now orchestrates and routes SGLang Wide-EP alongside vLLM through one Kubernetes stack.

On top of that integration, SGLang's `HiCache` keeps long-context agent sessions alive as traffic grows: run `L1 + L2` host RAM on steady single-pod deployments, and add `Shared L3` when pod evictions, cold starts, or multi-replica failover matter. Ready-to-run configurations are available in [`guides/models/glm-5-2`](https://github.com/llm-d/llm-d/tree/main/guides/models/glm-5-2).

## What’s next

We are working to connect SGLang's disaggregated Rust preprocessing layer (`sglang-processor`—already shared across SGLang's router, standalone renderer, and per-rank Rust servers) with `llm-d`'s router so prompts are rendered and tokenized once at ingress without router-to-worker token drift. Pairing that shared preprocessing with per-rank Rust metrics and KV-cache event streaming across `L1`, `L2`, and `L3` will move SGLang routing in `llm-d` from approximate prefix tracking to exact, block-level cache awareness.
