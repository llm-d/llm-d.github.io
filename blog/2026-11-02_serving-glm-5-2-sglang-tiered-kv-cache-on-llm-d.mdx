# Serving GLM-5.2 on SGLang with llm-d: Wide-EP, Host DRAM, and Shared Storage

In [Serving GLM-5.2 for Agentic Workloads on llm-d](/blog/serving-glm-5-2-agentic-workloads-on-llm-d), we showed how `llm-d` serves [GLM-5.2-FP8](https://huggingface.co/zai-org/GLM-5.2-FP8) (744B total parameters, 39B active, 78 layers) on NVIDIA H200 GPUs by combining wide expert parallelism (`DEP`), prefill/decode (`P/D`) disaggregation, prefix-cache-aware routing, Multi-Token Prediction (`MTP`), and CPU DRAM offloading. That post closed by pointing to the next architectural step: extending the KV cache hierarchy beyond per-node CPU DRAM to shared network storage so paused agent sessions, cross-rank spills, and restarted or scaled-out prefill replicas can restore saved KV state instead of recomputing repository-scale prompts.

This post puts that stack into practice and benchmarks it end to end on the **SGLang** variant of the [GLM-5.2 well-lit path](https://github.com/llm-d/llm-d/tree/main/guides/models/glm-5-2) (`MODEL_SERVER=sglang`), running SGLang `v0.5.23` on two 8-GPU NVIDIA H200 nodes (`p1w1d1w1`, 16 GPUs total) behind the `llm-d` inference router. Using SGLang's Hierarchical Cache (**HiCache**) on the prefill pool, we evaluate a three-tier KV cache hierarchy under data-parallel attention (`DEP8`: attention `TP=1, DP=8, EP=8`):

* **L1 GPU HBM:** Per-rank high-bandwidth memory on each prefill GPU (`261,376` tokens per rank, `2.09M` tokens per node at `--mem-fraction-static 0.90`), paired with `383,552` tokens per rank (`3.07M` per node at `0.945`) on decode.
* **L2 host DRAM:** Per-rank pinned host memory managed by SGLang HiCache (`98.4 GiB/rank` default via `--hicache-size 100` = `15.44M` tokens per node, scaling to `147.5 GiB/rank` via `--hicache-size 150` = `23.16M` tokens per node) using `direct` PCIe Gen5 DMA transfers (`page_first_direct`).
* **Shared L3 storage:** SGLang HiCache's file storage backend (`--hicache-storage-backend file`) backed by a `ReadWriteMany` PersistentVolumeClaim (`hicache-fs`), providing a single deduplicated cache pool shared across all attention-DP ranks and prefill replicas. The backend's client-side metadata cache is enabled, so each rank remembers which pages already exist (scanned at startup and updated on every write and read) instead of asking the filesystem's metadata server for every page.

Every load-sweep claim in this post uses the [AIPerf](https://github.com/ai-dynamo/aiperf) `900s` benchmark protocol (`--scenario inferencex-agentx-mvp --public-dataset semianalysis_cc_traces_weka_with_subagents --max-context-length 142000`) and the paused multi-turn conversation design from the [earlier vLLM GLM-5.2 post](/blog/serving-glm-5-2-agentic-workloads-on-llm-d), which gives a common workload protocol for an indicative comparison with those vLLM wide-EP runs.

## The shape of agentic traffic

As analyzed in the [vLLM GLM-5.2 post](/blog/serving-glm-5-2-agentic-workloads-on-llm-d#the-shape-of-agentic-traffic), interactive coding agents spend almost all of their token budget re-reading growing repository state across tool executions and subagent waves. In the [`semianalysisai/cc-traces-weka-062126`](https://huggingface.co/datasets/semianalysisai/cc-traces-weka-062126) production Claude Code trace corpus (`393` sessions, `98,827` requests: `56,798` main-agent turns and `42,029` subagent calls across `1,697` parallel fan-out groups), each turn appends a tool result or diff to the prior conversation prefix:

| **Main-agent metric (`cc-traces-weka-062126`)** | **p50** | **p90** | **p99** |
| :--- | :--- | :--- | :--- |
| Input tokens per request (full corpus, 393 sessions) | 254K | 651K | 898K |
| Input tokens per request (`<=142K` single-node `DEP8` subset) | 54.4K | 100.2K | 131.7K |
| Output tokens per response | 616 | 3,502 | 10,346 |
| Input-length growth from prior turn | 1,728 | 5,440 | 124.6K |
| Post-response think gap (after prior turn completes) | 5.1 s | 2.3 min (140 s) | 55.9 min (3,354 s) |
| Turns per session | 65 | 330 | 1,390 |
| Prefix overlap with best earlier turn | 99.45% | 99.91% | 100.0% |
| Subagent group fan-out size (`1,697` groups) | 16 | 47 | 175 |

*Note on corpus versions and gap definitions:* This table summarizes all `393` sessions in the public `cc-traces-weka-062126` release and measures the **post-response think gap** (`next_arrival - prev_completion`). The earlier vLLM post summarized an initial `219`-session release (`195K` median input, `317` median output) and reported **inter-call wall-clock arrival gaps** (`2 s` p50 / `24 s` p90 / `11.4 min` p99). Both `900s` AIPerf sweeps replay the identical `semianalysis_cc_traces_weka_with_subagents` preset, and our paused-session replay uses the earlier `2.1 s` / `25.8 s` target pause schedule for comparability.

Three workload characteristics directly shape the KV cache design:

1. **Prefill dominates compute whenever prefixes miss cache.** Over `95.5%` of main-agent turns reuse at least `90%` of their prompt verbatim from an earlier turn, reading `50K–250K` input tokens to emit `~300–600` output tokens.
2. **Inter-turn pauses span three orders of magnitude.** Quick CLI tool calls return in `2–5 seconds`, whereas test-suite runs, human code reviews, and developer context switches stretch pauses from minutes to nearly an hour (`55.9 min` p99), long enough for active traffic to evict idle sessions from GPU HBM and eventually host DRAM.
3. **Subagent bursts and load balancing force cross-rank reads.** Over `42%` of requests arrive in concurrent subagent fan-out groups (`16` parallel requests at p50, `47` at p90) sharing a parent repository context across multiple data-parallel attention ranks.

## How the SGLang wide-EP deployment works

The SGLang GLM-5.2 recipe in [`guides/models/glm-5-2/modelserver/gpu/sglang`](https://github.com/llm-d/llm-d/tree/main/guides/models/glm-5-2/modelserver/gpu/sglang) deploys disaggregated prefill and decode pools via a Kubernetes `DisaggregatedSet` (two `LeaderWorkerSet` groups) fronted by the `llm-d` inference router (`Endpoint Picker` + Envoy):

Five components work together in the SGLang `v0.5.23` stack on 8-GPU H200 nodes (tested on GKE A3 Ultra `a3-ultragpu-8g` with 8x ConnectX-7 RoCE NICs via Dynamic Resource Allocation):

* **Per-rank Rust HTTP listeners + `sglang-processor` (`SGLANG_RUST_SERVER=1`):** Rather than funneling 8 GPUs through one Python FastAPI process, each attention-DP rank runs its own Rust HTTP server (`:8000–8007` on prefill, `:8200–8207` behind the local `routing-proxy` on decode) with native Rust chat-template rendering and tokenization (`sglang-processor` in `v0.5.23`). All eight ports are registered in the `InferencePool` so the inference router dispatches directly to the rank holding the warm prefix.
* **`deepep_v2` `hybrid` MoE dispatch:** Both pools run data-parallel attention with expert parallelism (`--tp-size 8 --attn-dp-size 8 --ep-size 8` on 1-node `DEP8`, or `16` on 2-node `DEP16`) using `--moe-a2a-backend deepep_v2 --deepep-v2-mode hybrid`, which dispatches over NVLink within a single node and combines inter-node NCCL GIN RDMA with NVLink across multi-node groups.
* **FlashMLA + DeepSeek Sparse Attention (`DSA`) lightning indexer:** GLM-5.2 pairs compressed FP8 MLA KV state (`--kv-cache-dtype fp8_e4m3`) with a 22-layer DSA lightning indexer (`--dsa-prefill-backend flashmla_kv --dsa-decode-backend flashmla_kv`, `page_size=64`). Both the MLA latent cache and the DSA indexer cache travel together across L1, L2, L3, and P/D RDMA transfers.
* **Mooncake GPUDirect RDMA with Linux `DMA-BUF`:** Prefill streams KV and indexer blocks to decode via the Mooncake transfer engine (`--disaggregation-transfer-backend mooncake`). Setting `WITH_NVIDIA_PEERMEM=0` registers HBM tensors through `ibv_reg_dmabuf_mr` on Container-Optimized OS with the NVIDIA open kernel driver, sustaining zero transfer errors across multi-hour load sweeps.
* **3-step EAGLE Multi-Token Prediction (`MTP`):** Both roles run 3-step EAGLE speculative decoding (`--speculative-algorithm EAGLE --speculative-num-steps 3 --speculative-num-draft-tokens 4 --speculative-moe-a2a-backend none`).

## Fitting repository-scale sessions in memory under `DEP8`

### Why data-parallel attention (`DEP8`) replaces `TP=8`

GLM-5.2's Multi-Head Latent Attention (`MLA`) compresses each token's KV state into a single shared latent vector instead of per-head K and V tensors. Standard tensor parallelism (`TP=8`) cannot shard that single latent across heads, so it **replicates identical copies of the MLA KV cache across all 8 GPUs**, shrinking effective node KV capacity by `8x`. Under `DEP8` (`TP=1, DP=8, EP=8` on attention), MoE expert weights are partitioned across all 8 GPUs while each GPU maintains an **independent KV pool** for the sessions routed to its port.

### Per-GPU HBM breakdown and multi-tier token capacity

To keep capacity arithmetic consistent across tiers, all memory figures below use **binary units (`KiB`, `MiB`, `GiB`, `TiB`)**. Note two SGLang conventions when reading raw logs and flags: SGLang's startup log prints `"GB"` for GPU HBM pools that are actually computed in binary `GiB` (`bytes / 2^30`, so `14.03 GiB / 261,376 tokens = 56.3 KiB/tok`), whereas `--hicache-size` (`HICACHE_SIZE_GB_PER_RANK`) specifies **decimal `GB` (`10^9` bytes)** for the host MLA+MTP KV pool before adding the DSA indexer pool (`--hicache-size 100` pins `93.13 GiB` MLA+MTP KV + `5.22 GiB` DSA indexer = `98.35 GiB/rank` at `53.4 KiB/tok`, making the MLA+MTP host pool about `7%` smaller than a binary `100 GiB/rank` cache).

## Tiered KV offloading under sustained load (`900s` stages)

We run `aiperf profile --scenario inferencex-agentx-mvp` (`--max-context-length 142000`, `900s` profiling window per concurrency after warmup, `0` failed requests across every run) across concurrency `16, 32, 64, 128` on three `16`-GPU `p1w1d1w1` arms:

1. **`L1 GPU HBM only` (`baseline`):** no host tier (`261.4K` L1 tokens/rank).
2. **`L1 + L2 Host DRAM` (`p1w1d1w1` default):** `98.4 GiB/rank` of pinned host DRAM behind L1 (`2.19M` L1+L2 tokens/rank).
3. **`L1 + L2 + Shared L3` (`hicache-fs`):** adds write-through persistence of every host page to a shared RWX filesystem (`9,000 GiB` Google Cloud Managed Lustre testbed volume), and waits for storage prefetches on a hit so a matched prefix is restored rather than recomputed.

Three clear patterns emerge across the 12 `900s` runs:

1. **The `2.09M`-token L1 HBM pool holds up through `c32`, then hits a cliff at `c64` (`38.1%` hit) and `c128` (`6.0%` hit).** With `261K` L1 tokens per rank, `baseline` comfortably serves `16–32` concurrent sessions (`2–4` per rank, `747.3 tok/s` output and `3.10 s` TTFT at `c32`). At `c64` (`8` sessions/rank, `~3.2M–4.5M` active tokens), active conversations evict one another between turns: server hit rate drops to `38.1%`, median TTFT jumps **17.8x** (`3.10 s -> 55.28 s`), and aggregate output falls backward to `456.0 tok/s`. At `c128`, L1 hit rate collapses to `6.0%`, median TTFT hits `174.19 s`, and output drops to `319.0 tok/s` while decode sits mostly idle (`11.15 ms` ITL, average decode batch `1.23`).
2. **HiCache L2 (`98.4 GiB/rank`) turns the `c64–c128` cliff into smooth scaling (`2.38x` and `3.94x` output).** Expanding node capacity to `17.53M` tokens keeps server hit rate at **`90.2%` (`c64`) and `88.5%` (`c128`)**. At `c64`, median TTFT drops **14.7x** (`55.28 s -> 3.77 s`) and output rises **2.38x** (`456.0 -> 1,085.1 tok/s`, `39.2 tok/s/user` end-to-end). At `c128`, input throughput reaches **`108,304 tok/s`** (`4.51x` baseline) and output reaches **`1,256.8 tok/s`** (`3.94x` baseline).
3. **`Shared L3` (write-through) stays within `8%–9%` of L2 output while raising median TTFT by `14%–33%`.** Across the sweep, `hicache-fs` persisted **`1,059,497` files (`529,748` pages = `33.9M` unique tokens = `1.77 TiB` on disk)** and completed `70` live cross-rank L3 prefetches when load-balancing spilled subagent branches to sibling DP ranks (`35` prefetches / `1.69M` tokens at `c128`), lifting server hit rate above L2-only at `c32` (`85.3% -> 91.6%`), `c64` (`90.2% -> 92.9%`), and `c128` (`88.5% -> 90.3%`). Median TTFT still rises by **`+14%` at `c16` (`3.49` vs. `3.05 s`), `+26%` at `c32` (`3.98` vs. `3.16 s`), `+33%` at `c64` (`5.00` vs. `3.77 s`), and `+30%` at `c128` (`26.03` vs. `20.09 s`)** (with similar `p90` shifts) despite the higher hit rate, for three reasons:
   * **Write-through backups compete with restores.** Every newly written host page is also written to storage by a per-rank background thread, which shares host memory bandwidth and Python execution time with the thread that restores pages from host DRAM to the GPU.
   * **Storage lookups for pages nobody has written yet.** Whenever a request carries pages that are not in host DRAM, the scheduler first checks whether they exist on the shared filesystem. The client-side metadata cache answers for pages a rank has already seen, but a brand-new page still costs one metadata lookup per 64-token page over the network before it can be prefilled.
   * **A cross-rank hit waits for the network read.** When a spilled subagent turn finds its prefix in Shared L3 instead of local DRAM, prefill waits for the remote read to finish (`~1.4 GiB/s` per rank from Lustre vs. `~42 GiB/s` from host DRAM over PCIe) in exchange for skipping GPU recomputation.

## Paused multi-turn sessions and cold-DRAM recovery from Shared L3

The `900s` AIPerf load sweep stresses active concurrency, while two real-world agentic regimes test capacity and persistence directly: **hundreds of ongoing conversations pausing between tool calls** (`~100K–105K` mean input tokens per turn) and **cold-DRAM events** (cross-rank spillover, multi-replica scale-out, or prefill pod restarts where local L1 and L2 start completely empty). To stay comparable with the earlier GLM-5.2 post's paused-conversation experiment, our multi-turn replay generator uses the same inter-turn pause distribution (`2.1 s` median / `25.8 s` p90 target; `2.3 s` median / `27.9 s` p90 realized in the 200-session window).

Three behaviors stand out across the three tiers:

* **`L1 + L2` (`--hicache-size 150` = `147.5 GiB/rank`, `25.25M` L1+L2 tokens/node) serves 200 paused `~100K`-token sessions on 16 GPUs at `5.39 s` median TTFT (`42.6x` faster than `L1-only`'s `229.5 s`) and `8.22 ms` median ITL**, restoring `2.69 TiB` of cached KV + indexer state across PCIe Gen5 at **`11.21 GiB/s` sustained** (`227,815` effective input `tok/s`). At `350` sessions (`~34.7M` active tokens), the working set exceeds a single prefill node's `25.25M`-token L1+L2 pool, dropping in-memory hit rate to `62.1%` (`36.89 s` TTFT, still `5.8x` faster than `L1-only`).
* **On warm `100–200` paused sessions, enabling `Shared L3` (write-through) adds `38%–43%` median TTFT (`7.55` and `7.71 s` vs. `5.46` and `5.39 s`) at the exact same `96.5%–96.6%` hit rate (`0` L3 reads).** Every turn appends `~3.5K` new tokens, so each turn also writes new pages to storage in the background and, because those pages are new, probes the filesystem for them (the client-side metadata cache only short-circuits pages that already exist). That background work competes with the restores from host DRAM to the GPU and lowers their effective throughput by `~20%` (`11.41 -> 9.14 GiB/s` at 100 sessions; `11.21 -> 8.86 GiB/s` at 200 sessions).
* **At `350` sessions, `Shared L3` (write-through) hit a cold-seeding bottleneck (`82.21 s` median TTFT, `17.43%` hit, only `55` turns completed in `449 s`).** Seeding `350 x ~100K` cold tokens in a single burst creates `~1.1M` new `.bin` and `.indexer.bin` files in a flat directory that already holds millions, which saturates per-rank file creation on the filesystem; host pages stay pinned until their storage write finishes, so subsequent turns could neither evict nor reuse host DRAM cleanly.

### 2. Cold-DRAM spillover and pod-restart recovery from Shared L3

Unlike local NVMe (which starts cold whenever a request lands on another replica or a pod is rescheduled onto a fresh node), Shared L3 (`hicache-fs`) decouples prefix survival from pod and node lifecycles. Because GLM-5.2's MLA KV cache is identical on every attention-DP rank, HiCache's file backend stores each 64-token page once under a rank-independent name, so any DP rank or prefill replica that mounts the volume can restore it:

| **Cold-DRAM Scenario (`0` tokens in L1 or L2)** | **Cold Recompute (No L3)** | **Shared L3 Restore (`hicache-fs`)** | **Warm L1/L2 Hit (Same Rank)** | **Data Restored from Shared L3** |
| :--- | :--- | :--- | :--- | :--- |
| **Cross-rank / post-restart (`16` sessions, `~92K` ISL, `conc=8`)** | `38.84 s` TTFT (`0.0%` hit, `17.3K` in `tok/s`) | **`16.82 s` TTFT (`-57%`, `2.31x` faster, `33.8K` in `tok/s`)** | `5.68 s` TTFT (`103.2K` in `tok/s`) | **`69.7 GiB` (`74.8 GB`, `1.44M` tok, `97.8%` hit, `16/16` sessions)** |
| **Full-pod cold-DRAM burst (`64` sessions, `~130K` ISL, `conc=16`)** | `236.00 s` TTFT (`0.0%` hit, `13.9K` in `tok/s`) | **`121.12 s` TTFT (`-49%`, `2.09x` throughput, `29.0K` in `tok/s`)** | `12.97 s` TTFT (`203.2K` in `tok/s`) | **`355.1 GiB` (`381.3 GB`, `7.10M` tok, `97.2%` hit, `56` L3 prefetches)** |

We also verified **prefill pod deletion and replacement** (`kubectl delete pod` on `wide-ep-sglang-glm-5-2-*-prefill-0`): as soon as the replacement pod became Ready with empty HBM and host DRAM, replaying a `59,904`-token session through the `llm-d` inference router immediately restored all `59,840` aligned prefix tokens from Shared L3 (`HiCache prefetch success: completed=59840 matched=0 loaded=59840`).

## Sizing `L2` host DRAM and `Shared L3` for agentic workloads

On an 8-GPU H200 (`a3-ultragpu-8g`, `2.95 TiB` host RAM) `DEP8` prefill node with `PREFILL_MEM_FRACTION_STATIC=0.90` (`4,084` GPU blocks/rank), each unit of `HICACHE_SIZE_GB_PER_RANK` (`10^9` bytes of MLA+MTP KV) adds `19,297` tokens (`301.5` 64-token blocks) of pinned MLA+MTP KV cache (`0.931 GiB`) plus `53.4 MiB` of DSA indexer cache per rank (`7.87 GiB` total node RAM per unit):

| Recommended Agentic Scenario | `HICACHE_SIZE_GB_PER_RANK` | L2 Tokens / Rank (`64`-tok blocks) | Node L2 RAM in `GiB` (KV + DSA Indexer) | Router `lruCapacityPerServer` (`L1 + L2`) |
| :--- | :--- | :--- | :--- | :--- |
| **Low concurrency** (`<= 16–32` active `~55K–85K`-token sessions/node) whose working set fits inside the `2.09M` L1 GPU HBM tokens | `0` (`baseline`) | `0` (`0`) | `0 GiB` | `4084` (`DEP8`) / `15072` (`DEP16`) |
| **Sustained high concurrency** (`64–128` active sessions/node; `17.53M` L1+L2 tokens/node). Fits inside the `1200Gi` request / `1600Gi` limit | `100` (recipe default) | `1,929,664` (`30,151`) | `745.1 + 41.8 GiB` (**`786.8 GiB`**) | `34235` (`DEP8`) / `45223` (`DEP16`) |
| **Long-pause interactive coding** (`150–250` concurrent `~100K`-token sessions/node; `25.25M` L1+L2 tokens/node). Raise pod memory to `1500Gi` / `1800Gi` | `150` (paused-session option) | `2,894,464` (`45,226`) | `1,117.6 + 62.6 GiB` (**`1,180.2 GiB`**) | `49310` (`DEP8`) / `60298` (`DEP16`) |
| **Multi-replica prefill pools** (`p2w1d1w2`, `p2w2d2w2`), **Spot/preemptible nodes, rolling restarts, subagent fan-out spills, and multi-hour pauses** (`p99 = 55.9 min`). Omit on single steady-state replicas to avoid the write-through TTFT cost (`+14%–33%` under sustained load, `+38%–43%` with paused sessions) | `+ hicache-fs` (Shared L3) | Shared RWX volume (`3.42 MiB/page`) | Shared across all replicas (`~19.6M` tok / `1 TiB`) | Keep at `L1 + L2` (`34235` or `49310`) |

:::tip Keep `lruCapacityPerServer` sized to `L1 + L2` when Shared L3 is enabled
`approx-prefix-cache-producer` tracks **per-rank** locality so `prefix-cache-affinity-filter` steers returning sessions back to the exact DP rank holding their prefix in DRAM (`5.4 s` TTFT vs. `16.8 s` from Shared L3). Because the Shared L3 volume is equally accessible from every rank and replica, keeping `lruCapacityPerServer` matched to `L1 + L2` preserves fast DRAM hits whenever pages remain in memory while Shared L3 automatically serves spills, cold starts, and restarts.
:::

## Running the recipe

The SGLang Wide-EP P/D recipe, the `hicache` (host DRAM) and `hicache-fs` (Shared L3) components, the router values, and the benchmark overlays (`baseline`, `hicache-fs`, `no-mtp`) live in [`guides/models/glm-5-2`](https://github.com/llm-d/llm-d/tree/main/guides/models/glm-5-2):

export REPO_ROOT=$(realpath $(git rev-parse --show-toplevel))
export GUIDE_NAME=glm-5-2
export NAMESPACE=llm-d-glm-5-2
source ${REPO_ROOT}/guides/env.sh

# 1. Deploy the llm-d inference router with the SGLang values (GPU + HiCache prefix index):
helm install ${GUIDE_NAME} \
  ${ROUTER_STANDALONE_CHART} \

kubectl apply -n ${NAMESPACE} \
  -k ${REPO_ROOT}/guides/models/glm-5-2/modelserver/gpu/sglang/deployments/p1w1d1w1
