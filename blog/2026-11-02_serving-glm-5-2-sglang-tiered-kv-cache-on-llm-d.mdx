# Serving GLM-5.2 on SGLang with llm-d: Wide-EP, Host DRAM, and Shared Storage

Interactive coding agents re-read repository-scale context on almost every turn, pause from seconds to nearly an hour while tests run or developers review diffs, and launch bursts of parallel subagents that share the same repository prefix. In [Serving GLM-5.2 for Agentic Workloads on llm-d](/blog/serving-glm-5-2-agentic-workloads-on-llm-d), we showed why GPU HBM fills up after only a handful of those sessions and how offloading evicted KV blocks to host DRAM keeps active conversations responsive. Yet host DRAM is still tied to one pod and one attention rank: whenever a prefill pod restarts, a Spot node is preempted, a pool scales out, or subagent bursts spill onto cold ranks, local memory starts empty and returning turns stall behind tens of seconds of GPU recomputation.

Extending the KV cache to shared network storage decouples saved prefixes from individual pods and ranks, at the cost of background write-through traffic and network lookups during normal serving. This post puts that stack into practice on the **SGLang** variant of the [GLM-5.2 well-lit path](https://github.com/llm-d/llm-d/tree/main/guides/models/glm-5-2), running [GLM-5.2-FP8](https://huggingface.co/zai-org/GLM-5.2-FP8) on two 8-GPU NVIDIA H200 nodes (`16` GPUs total) behind the `llm-d` inference router, in two parts:

1. **Supporting GLM-5.2 Wide-EP on SGLang with `llm-d`:** how per-rank Rust HTTP servers, data-parallel attention with `deepep_v2` MoE dispatch, FlashMLA with DeepSeek Sparse Attention indexing, Mooncake `DMA-BUF` RDMA, and 3-step Multi-Token Prediction (`MTP`) fit together on `DEP8`.
2. **Tiered KV offloading and when shared storage is worth it:** benchmarking SGLang's Hierarchical Cache (**HiCache**) across GPU HBM (`L1`), host DRAM (`L2`), and a shared `ReadWriteMany` filesystem (`Shared L3`) under sustained load, paused multi-turn conversations, and cold-DRAM or pod-restart recovery.

* **Wide-EP (`DEP8`) gives each prefill GPU its own `261K`-token `L1` KV pool (`2.09M` tokens per node), extended by one to two orders of magnitude across host DRAM and shared storage.** Data-parallel attention avoids duplicating GLM-5.2's unshardable MLA cache across all eight GPUs, while per-rank Rust HTTP listeners and Mooncake `DMA-BUF` RDMA keep prefix-aware routing and prefill-to-decode transfers scalable.

* **3-step EAGLE Multi-Token Prediction (`MTP`) halves decode inter-token latency (`34.9 ms` → `16.4 ms` at `c128`) and raises output `1.15x–1.62x` at matched concurrency.** Under a `30 tok/s/user` interactivity floor, `no-mtp` tops out at concurrency `16` (`164.4 tok/s`), whereas MTP sustains `39.2 tok/s/user` through concurrency `64` (`1,085.1 tok/s` — **`6.6x` higher interactive output comparing `c64` against `c16`**).

* **HiCache `L2` host DRAM (`98.4 GiB/rank` over direct PCIe DMA) prevents `L1` thrashing past concurrency `32` and raises `c128` output `3.94x`.** Without host offloading, server hit rate collapses to `6.0%` at `c128` (`174.2 s` median TTFT); adding `L2` DRAM holds hit rates at `85.3%–94.8%` and reaches **`1,256.8 tok/s` output at `c128` (`20.1 s` TTFT)**.

* **Rank-independent `Shared L3` storage (`hicache-fs`) cuts cold-DRAM recovery TTFT by `49%–57%`, trading `+14%–33%` median TTFT under sustained load (`+38%–43%` on warm paused sessions).** When sessions land on cold DP ranks or restarted prefill pods with empty DRAM, restoring prefixes from the shared RWX volume drops 16-session median TTFT from `38.8 s` to **`16.8 s` (`2.31x` faster)** — making DRAM-only `hicache` best for single steady-state replicas and `hicache-fs` suited to multi-replica, Spot, or restart-tolerant pools.

## Supporting GLM-5.2 Wide-EP on SGLang with `llm-d`

The SGLang GLM-5.2 recipe in [`guides/models/glm-5-2/modelserver/gpu/sglang`](https://github.com/llm-d/llm-d/tree/main/guides/models/glm-5-2/modelserver/gpu/sglang) deploys disaggregated prefill and decode pools through a Kubernetes `DisaggregatedSet` (two `LeaderWorkerSet` groups) behind the `llm-d` inference router (`Endpoint Picker` + Envoy):

Prefill ranks manage L1 GPU HBM, L2 host DRAM (<code>98.4–147.5 GiB/rank</code> via direct PCIe DMA), and a shared L3 RWX storage volume, then transfer KV and DSA indexer pages to decode over Mooncake DMA-BUF RDMA.
</Figure>

Five components work together in the SGLang `v0.5.23` stack on 8-GPU H200 nodes (tested on GKE A3 Ultra with 8x ConnectX-7 RoCE NICs via Dynamic Resource Allocation):

* **Per-rank Rust HTTP listeners and `sglang-processor`:** Rather than funneling eight GPUs through one Python HTTP server, each attention-DP rank exposes its own Rust HTTP listener (`:8000–8007` on prefill, `:8200–8207` behind the local `routing-proxy` on decode) with native Rust chat-template rendering and tokenization. Registering all eight ports in the `InferencePool` lets the inference router steer returning turns directly to the rank holding the warm prefix.
* **Data-parallel attention (`DEP8`) with `deepep_v2` `hybrid` MoE dispatch:** As detailed in the [earlier GLM-5.2 post](/blog/serving-glm-5-2-agentic-workloads-on-llm-d#fitting-repository-scale-sessions-in-memory), GLM-5.2's Multi-Head Latent Attention (`MLA`) stores one shared latent vector per token that standard tensor parallelism would duplicate across all eight GPUs. Running data-parallel attention alongside expert parallelism (`TP=1, DP=8, EP=8` on one node, or `16` across two nodes) partitions MoE weights across GPUs while giving every rank an independent KV pool, using `deepep_v2` `hybrid` to dispatch tokens over NVLink within a node and NCCL GIN RDMA across nodes.
* **FlashMLA and DeepSeek Sparse Attention (`DSA`) indexing:** GLM-5.2 pairs FP8 MLA KV state with a 22-layer DSA lightning indexer in 64-token pages. Both the MLA cache and the DSA indexer cache move together across `L1`, `L2`, `L3`, and prefill-to-decode RDMA transfers.
* **Mooncake GPUDirect RDMA over Linux `DMA-BUF`:** Prefill streams KV and indexer blocks to decode via the Mooncake transfer engine. Setting `WITH_NVIDIA_PEERMEM=0` registers GPU memory through `ibv_reg_dmabuf_mr`, sustaining error-free GPUDirect RDMA on Container-Optimized OS with the NVIDIA open kernel driver without legacy `nvidia_peermem`.
* **3-step Multi-Token Prediction (`MTP`) via EAGLE:** Both pools drive GLM-5.2's built-in 1-layer NextN draft head through SGLang's 3-step EAGLE speculative-decoding loop, proposing three draft tokens per decode step and verifying four tokens in one target forward pass.

### Memory fit across GPU HBM, host DRAM, and shared storage

On a single 8-GPU `DEP8` prefill node, `261,376` `L1` tokens per rank comfortably fits our `142,000`-token per-request admission cap with `119K` tokens of spare headroom, yet the entire node holds only `2.09M` tokens in HBM — roughly 20 to 35 repository-scale sessions before active turns start evicting one another. Adding pinned host DRAM via HiCache expands node capacity by an order of magnitude (`17.5M–25.3M` tokens), and mounting a shared `ReadWriteMany` volume (`9,000 GiB` Google Cloud Managed Lustre instance in our testbed) adds a `~163M`-token deduplicated pool shared across all ranks and replicas:

Across all four stages, GLM-5.2's MTP head averages **`2.97` accepted tokens per verification step**, cutting median inter-token latency by **48%–53%** and raising total output by **`1.15x–1.62x` at matched concurrency** (`1.41x` at `c64`). The larger practical gain appears when enforcing a **`30 tok/s/user` interactivity bar**: without MTP, per-user throughput drops below `30 tok/s/user` past `c16` (`164.4 tok/s`), whereas MTP sustains `39.2 tok/s/user` at `c64` (`1,085.1 tok/s`) — **`6.6x` higher interactive output comparing `c64` with MTP against `c16` without MTP**.

At `c128`, `no-mtp` reports a lower median TTFT (`11.66 s` vs. `20.09 s`) even though it finishes fewer turns and produces `18%` less output. Because slower decode keeps simulated users in generation more than twice as long, fewer of the 128 users return to the prefill queue at the same time (and disabling the draft head also skips draft-layer work during prefill), illustrating why lower TTFT alone does not indicate better overall performance.

## Tiered KV offloading: host DRAM and the Shared L3 trade-off

With the `16`-GPU `p1w1d1w1` Wide-EP stack and EAGLE MTP held fixed, we evaluate three prefill cache configurations to separate what local host DRAM solves from where shared storage pays off:

1. **`L1 GPU HBM only` (`benchmark/baseline/p1w1d1w1`):** GPU memory only (`261.4K` tokens/rank).
2. **`L1 + L2 Host DRAM` (`p1w1d1w1` default):** adds pinned host DRAM behind `L1` via direct PCIe Gen5 DMA (`page_first_direct`).
3. **`L1 + L2 + Shared L3` (`benchmark/hicache-fs/p1w1d1w1`):** adds write-through persistence of host pages to a shared `ReadWriteMany` filesystem (`9,000 GiB` Managed Lustre volume) with HiCache's client-side metadata cache enabled so each rank remembers pages it has already written or read, and waits for storage prefetches on a hit so matched prefixes are restored rather than recomputed.

Because a steady-state load sweep only exercises warm local memory, we test all three configurations across **sustained concurrency**, **paused multi-turn sessions**, and **cold-DRAM recovery**.

Three clear patterns emerge across the 12 runs:

1. **`L1` HBM holds up through `c32`, then thrashes at `c64` and `c128`.** While 16 to 32 active sessions fit inside the `2.09M`-token node `L1` pool (`3.1 s` median TTFT), scaling to `c64` and `c128` causes active conversations to evict one another between turns. Server hit rate falls to `38.1%` and then `6.0%`, median TTFT climbs to `174.2 s`, and total output drops backward to `319.0 tok/s` while decode sits mostly idle.
2. **`L2` host DRAM turns that cliff into smooth scaling (`3.94x` `c128` output).** Adding `98.4 GiB/rank` of pinned host DRAM holds server hit rates at `85.3%–94.8%` across the full sweep. At `c64`, median TTFT drops from `55.3 s` to `3.77 s` while output more than doubles to `1,085.1 tok/s`; at `c128`, input throughput reaches `108,304 tok/s` and total output reaches `1,256.8 tok/s` — saturating the single `DEP8` prefill node (`98.8%` of processed tokens are input tokens).
3. **Write-through `Shared L3` stays within `8%–9%` of `L2` output while adding `14%–33%` to median TTFT.** Across the sweep, `hicache-fs` persisted `33.9M` unique tokens (`1.77 TiB`) to shared storage and completed `70` live cross-rank restores when load balancing spilled subagent branches onto sibling DP ranks, lifting hit rates slightly above `L2`-only from `c32` through `c128`. Median TTFT still rises by `14%–33%` across stages for three reasons:
   * **Write-through backups compete with restores.** A background thread on each rank writes newly created host pages to storage, sharing host memory bandwidth and Python execution time with DRAM-to-GPU restores.
   * **Brand-new pages still check the filesystem.** The client-side metadata cache avoids network calls for pages a rank has already seen, but every unseen 64-token page still pays one remote metadata lookup before prefill proceeds.
   * **Cross-rank L3 hits wait on network reads.** When a spilled subagent turn restores its prefix from shared storage rather than local DRAM, prefill waits for the network read (`~1.4 GiB/s` per rank vs. `~42 GiB/s` over local PCIe) in exchange for skipping GPU recomputation.

*Note on `Hit %`:* SGLang's `#cached-token` counter reports all prompt tokens satisfied from cache (`L1`, `L2`, or `L3`) without GPU recomputation.

* **`L2` host DRAM keeps 200 paused `~100K`-token sessions interactive on 16 GPUs.** Across `100` and `200` sessions, `96.5%–96.6%` of prompt tokens restore from host DRAM at over `11 GiB/s` sustained, holding median TTFT near `5.4 s` versus `221–230 s` on `L1` alone. At `350` sessions (`~34.7M` active tokens), the working set outgrows a single prefill node's `25.25M`-token `L1+L2` pool, dropping the hit rate to `62.1%` (`36.89 s` TTFT).
* **On warm `100–200` sessions, write-through `Shared L3` adds `38%–43%` median TTFT with zero `L3` reads.** Because active prefixes remain in local DRAM, storage never serves a read hit here, yet persisting each turn's `~3.5K` newly appended tokens in the background reduces effective DRAM-to-GPU restore throughput by roughly `20%` (`7.55–7.71 s` vs. `5.39–5.46 s` TTFT).
* **At `350` cold-seeded sessions, `Shared L3` hit a file-creation stall — and the `82.21 s` median understates it because only `55` turns finished.** Bursting `350` uncached `~100K`-token sessions at once creates roughly `1.1M` new `.bin` and `.indexer.bin` files in a single flat directory, saturating per-rank file creation while host pages stay pinned until their storage writes finish. Whereas the `100`- and `200`-session runs completed `435–570` turns in `~250 s`, **only `55` turns finished during the `449 s` window at `350` sessions** while the remaining `~84%` of sessions stayed queued behind pinned host pages — so `82.21 s` reflects only the earliest completions rather than the full stall.

### 3. Cold-DRAM spillover and pod-restart recovery from Shared L3

Where `Shared L3` pays off is whenever local `L1` and `L2` memory is empty — during cross-rank spillover, prefill scale-out, Spot node replacement, or rolling restarts. Because GLM-5.2's MLA KV state is identical across attention-DP ranks, HiCache's file backend writes each 64-token page once under a rank-independent key, allowing any DP rank or replacement prefill pod mounting the `ReadWriteMany` volume to restore it directly:

| **Cold-DRAM Scenario (`0` tokens in L1 or L2)** | **Cold Recompute (No L3)** | **Shared L3 Restore (`hicache-fs`)** | **Warm L1/L2 Hit (Same Rank)** | **Data Restored from Shared L3** |
| :--- | :--- | :--- | :--- | :--- |
| **Cross-rank / post-restart (`16` sessions, `~92K` ISL, `conc=8`)** | `38.84 s` TTFT (`0.0%` hit, `17.3K` in `tok/s`) | **`16.82 s` TTFT (`-57%`, `2.31x` faster, `33.8K` in `tok/s`)** | `5.68 s` TTFT (`103.2K` in `tok/s`) | **`69.7 GiB` (`74.8 GB`, `1.44M` tok, `97.8%` hit, `16/16` sessions)** |
| **Full-pod cold-DRAM burst (`64` sessions, `~130K` ISL, `conc=16`)** | `236.00 s` TTFT (`0.0%` hit, `13.9K` in `tok/s`) | **`121.12 s` TTFT (`-49%`, `2.09x` throughput, `29.0K` in `tok/s`)** | `12.97 s` TTFT (`203.2K` in `tok/s`) | **`355.1 GiB` (`381.3 GB`, `7.10M` tok, `97.2%` hit, `56` L3 prefetches)** |

We also verified **live prefill pod deletion and replacement** (`kubectl delete pod` on the prefill `LeaderWorkerSet` pod): as soon as the replacement pod became Ready with empty HBM and host DRAM, replaying a `59,904`-token session through the `llm-d` inference router immediately restored all `59,840` page-aligned prefix tokens from `Shared L3` (`HiCache prefetch success: completed=59840 matched=0 loaded=59840`) without recomputing the prompt.

## When is Shared L3 worth it? Sizing `L2` and `L3`

Putting the steady-state overhead and cold-recovery numbers together gives a clear rule for deciding which tiers to enable:

* **Stop at `L1 + L2` host DRAM (`hicache`) on single steady-state prefill replicas.** When one prefill pod holds the active working set in host RAM (`<= 25M` tokens) and restarts are rare, omitting `hicache-fs` avoids the `+14%–33%` sustained-load (`+38%–43%` paused-session) write-through TTFT overhead.
* **Add `Shared L3` (`hicache-fs`) when prefixes must survive across pods, nodes, or long idle gaps.** Multi-replica prefill pools (`p2w1d1w2`, `p2w2d2w2`), Spot or preemptible GPU nodes, rolling upgrades, large subagent fan-outs that spill across ranks or replicas, and multi-hour session pauses that evict host DRAM all benefit from cutting cold-DRAM TTFT roughly in half (`38.8 s` → `16.8 s`). When seeding a cold volume, ramp traffic gradually rather than bursting hundreds of uncached `100K`-token sessions simultaneously.

| Recommended Agentic Scenario | `HICACHE_SIZE_GB_PER_RANK` | L2 Tokens / Rank (`64`-tok blocks) | Node L2 RAM in `GiB` (KV + DSA Indexer) | Router `lruCapacityPerServer` (`L1 + L2`) |
| :--- | :--- | :--- | :--- | :--- |
| **Low concurrency** (`<= 16–32` active `~55K–85K`-token sessions/node) whose working set fits inside the `2.09M` L1 GPU HBM tokens | `0` (`baseline`) | `0` (`0`) | `0 GiB` | `4084` (`DEP8`) / `15072` (`DEP16`) |
| **Sustained high concurrency** (`64–128` active sessions/node; `17.53M` L1+L2 tokens/node). Fits inside the `1200Gi` request / `1600Gi` limit | `100` (recipe default) | `1,929,664` (`30,151`) | `745.1 + 41.8 GiB` (**`786.8 GiB`**) | `34235` (`DEP8`) / `45223` (`DEP16`) |
| **Long-pause interactive coding** (`150–250` concurrent `~100K`-token sessions/node; `25.25M` L1+L2 tokens/node). Raise pod memory to `1500Gi` / `1800Gi` | `150` (paused-session option) | `2,894,464` (`45,226`) | `1,117.6 + 62.6 GiB` (**`1,180.2 GiB`**) | `49310` (`DEP8`) / `60298` (`DEP16`) |
| **Multi-replica prefill pools** (`p2w1d1w2`, `p2w2d2w2`), **Spot/preemptible nodes, rolling restarts, subagent fan-out spills, and multi-hour pauses**. Omit on single steady-state replicas to avoid the write-through TTFT cost (`+14%–33%` under sustained load, `+38%–43%` with paused sessions) | `+ hicache-fs` (Shared L3) | Shared RWX volume (`3.42 MiB/page`) | Shared across all replicas (`~19.6M` tok / `1 TiB`) | Keep at `L1 + L2` (`34235` or `49310`) |

:::tip Keep `lruCapacityPerServer` sized to `L1 + L2` when Shared L3 is enabled
`approx-prefix-cache-producer` tracks **per-rank** locality so `prefix-cache-affinity-filter` steers returning sessions back to the exact DP rank holding their prefix in DRAM (`5.4 s` TTFT vs. `16.8 s` from Shared L3). Because the Shared L3 volume is equally accessible from every rank and replica, keeping `lruCapacityPerServer` matched to `L1 + L2` preserves fast DRAM hits whenever pages remain in memory while Shared L3 automatically serves spills, cold starts, and restarts.
:::

## Running the recipe

The SGLang Wide-EP P/D recipe, the `hicache` (host DRAM) and `hicache-fs` (Shared L3) components, the router values, and the benchmark overlays (`baseline`, `hicache-fs`, `no-mtp`) live in [`guides/models/glm-5-2`](https://github.com/llm-d/llm-d/tree/main/guides/models/glm-5-2):

```bash
export REPO_ROOT=$(realpath $(git rev-parse --show-toplevel))
export GUIDE_NAME=glm-5-2
export NAMESPACE=llm-d-glm-5-2
source ${REPO_ROOT}/guides/env.sh

# 1. Deploy the llm-d inference router with the SGLang values (GPU + HiCache prefix index):
helm install ${GUIDE_NAME} \
  ${ROUTER_STANDALONE_CHART} \
  -f ${REPO_ROOT}/guides/recipes/router/base.values.yaml \
  -f ${REPO_ROOT}/guides/models/${GUIDE_NAME}/router/${GUIDE_NAME}.values.yaml \
  -f ${REPO_ROOT}/guides/models/${GUIDE_NAME}/router/sglang.values.yaml \
  -n ${NAMESPACE} --version ${ROUTER_CHART_VERSION}

# 2a. Deploy the default 16-GPU p1w1d1w1 (EAGLE MTP + 98.4 GiB/rank L2 host DRAM):
kubectl apply -n ${NAMESPACE} \
  -k ${REPO_ROOT}/guides/models/glm-5-2/modelserver/gpu/sglang/deployments/p1w1d1w1

# 2b. Or include Shared L3 storage on the llm-d-kv-cache-storage RWX PVC:
kubectl apply -n ${NAMESPACE} \
  -k ${REPO_ROOT}/guides/models/glm-5-2/modelserver/gpu/sglang/deployments/benchmark/hicache-fs/p1w1d1w1
```
